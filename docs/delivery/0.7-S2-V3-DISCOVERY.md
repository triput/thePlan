## 12. Tesla code map (Discovery only)

**Status:** map of the tree on `feature/0.7-s1-first-slice` as of 2026-10-13. **No V3 behavior is implemented.** `candidates.py` does not decide eligibility.

### 12.1 Where the placer decides a workday

| Step | Where | What it does today |
| --- | --- | --- |
| Inheritance | `scheduler/collect.py` → `windows.effective_preferred_time_window_id` | Task FK, else project, else epic, else `None`. |
| Call | `scheduler/calculate.py` `place_one_block(..., preferred_window_id=effective_window_by_task[task])` | Resolved id, not a second lookup. |
| Gate | `placement.is_workday` | `day.weekday() < settings.workweek_days`. Zero matches nothing. Not a weekday mask. Tue–Sat stored on Working still makes Monday eligible when `workweek_days == 5`. |
| Clip | `placement.workday_bounds` | One interval: `workday_start_local` + `workday_minutes` in `settings.timezone`, then UTC. Can cross midnight as a single span. |
| Search | `placement._search_windows_for_day` | Non-workday → `[]`. Unbound (`preferred is None`) → that one interval, tier `None`. Bound → green, then yellow, then (non-strict) full-workday neutral, each clipped by `_clip_band_to_workday` and with red subtracted. |
| Why empty | `placement._map_block_reason` | Same `is_workday` / `workday_bounds` gate. |
| Day loop | `place_task` | Local dates from `now` through `horizon_end`. Overrides via `effective_day_map` before search. |
| Second consumer | `pin_reservation._uncovered_outside_working` | Same `is_workday` + `workday_bounds` for `CONFLICT_OUTSIDE_WORKING`. |
| Override date | `time_map_overrides.effective_local_date_for_scheduling_day` | Anchors on `workday_start_local`, not a policy window. Web mirror: `apps/web/src/timeMapOverrides.ts`. |
| Bands | `placement.band_bounds` | Wall clock in operator zone. Bit `1 << weekday`. Midnight-crossing bands are rejected at write (`focus_windows.validate_bands`, `time_map_overrides.validate_override_bands`). |

`place_task` falls back to `task.preferred_time_window_id` only when the caller omits `preferred_window_id`. Calculate does not omit it. A V3 General branch must key off that resolved id (`None` = unclassified), not the task FK alone.

### 12.2 Unclassified path vs required General link

Today, resolved id `None` never loads `availability_policies.slug = general`. It returns the legacy workday interval.

`task_scheduling_effective._build_sources` labels that `legacy_unclassified` with `placer_active: true`, and `availability_general` with `placer_active: false`. `general_policy_scheduling_effective` is hardcoded `False`. Route `availability_policies._policy_out` sets `scheduling_effective: false` for every slug.

General PATCH (`update_policy`, non-`work`) stores windows and does **not** bump `scheduling_revision` (legacy **F6**). V3: unclassified eligibility = those General windows only. Do not copy hours onto the task. Do not write `preferred_time_window_id` (**F14**). Do not union Working or Personal (**F13**).

### 12.3 Mapped unconverted: map ∩ workweek vs map ∩ Working

Today the clip is `intersect_ranges(workday_bounds, band_bounds)`. One map wins (task > project > epic). Strict has no neutral. Non-strict neutral is the **entire** legacy workday minus red, including on banded days (**F18** — keep that shape; the neutral set becomes the Working windows, not “unbanded days only”).

Override replaces that day’s bands and strict (`effective_day_map`). Red is per effective map only (**F9**). Empty strict stays empty (**F3**). General edits must not move this task (**F2**, **F4**, **F6**).

V3 clip target is stored **Working** windows (weekday mask + each window’s start/duration/`ends_next_day`), including Tue–Sat, weekend-only, and empty Working = no days. Do not remap those weekdays into `workweek_days` (**F7**).

`effective_windows_for_date` is the wrong clip helper: it filters `window.weekday == on.weekday()` and its provenance string says the placer does not consume policies. It does not emit an overnight tail onto the next calendar date.

### 12.4 Mirror writes that must stop

Only `availability_policies._sync_workweek_from_working_windows`, called from `update_policy` when slug is `work` and `windows` is in the body.

| Working PATCH | Stored on policy? | `workweek_*` write | Revision bump |
| --- | --- | --- | --- |
| Empty `windows: []` | Yes | `workweek_days = 0`; clocks unchanged | Yes |
| Monday-first, one window, same start and duration | Yes | `workweek_days = len`, start, minutes | Yes |
| Contiguous same-hours, not Monday-first (Tue–Sat, weekend) | Yes | **No** (returns false) | **No** |
| Duplicate weekday, gap, or mixed hours | **No** — 422 `WORKING_POLICY_AMBIGUOUS` / `NONCONTIGUOUS` / `HETEROGENEOUS` | No | No |

Settings PATCH does not push onto policies (**F16**). Personal window writes 422 `PERSONAL_WINDOWS_LOCKED` (**F15**). Leave that lock for V3; Personal is not an eligibility source.

Any Working or General window write that changes eligible intervals must take `lock_owner_scheduling` and `increment_scheduling_revision`, including Tue–Sat and General. ### 12.6 Fingerprint categories that must gain `availability`

Live snapshots are already v4 (`live_snapshot_version`). `SCHEDULING_ACTIVATIONS` is only `s2-v1-duration-bounds` and `s2-v2-pin-reservation`.

`assemble_snapshot` puts `workday_start_local`, `workday_minutes`, and `workweek_days` inside `timezone_horizon_workweek`. `outcomes` snapshot builders pass those from `user_settings`. There is no `availability` key. `COMPARED_STALE_CATEGORIES` does not include one. `DEFERRED_STALE_CATEGORIES` is only `priority_ups`.

V3 activation (same pattern as V1/V2, not a V5 wait):

- Append a stable token, e.g. `s2-v3-working-general-availability`, to `SCHEDULING_ACTIVATIONS`.
- Add compared category `availability`: Working windows, General windows, and the unclassified-vs-mapped choice only insofar as a purpose link changes eligible windows. Dated add/replace of **policy** windows belongs here when that write exists; Time Map overrides stay in `time_map_overrides`.
- Remove the three workday fields from `timezone_horizon_workweek` in the same change. Timezone, horizon days, and `inter_block_buffer_minutes` stay.
- Do not hash `map_style` or `time_map_overrides` into `availability`. Do not hash `nominal_workday_minutes`.
- Previews missing the token stale as `scheduling_activation` (`owner_snapshot_predates_activation` / apply `PREVIEW_STALE`). Do not rewrite historical explanation JSON.
- Bump `scheduling_revision` once at activation (owner lock), same idea as chunking cutover.

Until that category exists, a General edit or a Tue–Sat Working edit does not change the fingerprint, because those writes do not touch `workweek_*`.

### 12.7 Split / overnight / DST — present vs missing

**Present**

- Policy row: `duration_minutes`, `ends_next_day`, `end_time` checks in `models/availability.py`. `derive_window_end` sets the flag when start+duration reaches the next midnight, including 24h.
- Schema allows multiple windows per weekday (no unique on weekday). Sort order exists.
- Legacy workday span can cross midnight as one interval (`timedelta` on the start).
- Band and override clocks use `ZoneInfo` + `astimezone`. Comments name spring-forward and fall-back. No fold argument is passed (`fold=0`).
- Map bands cannot cross midnight; writers tell the operator to split them.

**Missing for A11b / SS-13**

- No materializer from `AvailabilityWindow` to UTC intervals. Placer never reads `ends_next_day`.
- No split-window union. Working PATCH rejects a second window on the same weekday, and rejects gaps and mixed hours, so those patterns cannot be stored yet.
- `effective_windows_for_date` does not attach Monday’s overnight tail to Monday’s occurrence (SPEC: the tail is part of the start-day window; replacing Monday replaces the Tuesday tail).
- No shared gap/fold/ambiguous rule. A local time in the spring-forward gap is whatever ZoneInfo does at `fold=0`.
- Override local-date match and the web copy still anchor on `workday_start_local`. Moving the clip without deciding this anchor will desync override selection from the UI on overnight and DST days.
