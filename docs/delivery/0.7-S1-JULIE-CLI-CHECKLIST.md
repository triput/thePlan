## How this slice is supposed to work

S1 provides configuration, read-back, and task progress foundations. Saving General availability does **not** make the scheduler place work inside those windows yet. Availability output must disclose `scheduling_effective: false`. The command named `availability effective` describes date-specific configuration in S1, not proven placement eligibility.

Working availability has a compatibility exception: a Monday-first, same-hours pattern can update the legacy working-hours settings. A Tuesday–Saturday or weekend-only pattern stays config-only and must leave those legacy settings unchanged. Noncontiguous or mixed-hours Working edits may reject in this slice. Personal windows remain locked empty. These are S1 limitations, not the intended final scheduling experience.

Task effort has three distinct values: **original estimate**, **time worked**, and **remaining estimate**. Creating a 120-minute task starts at 120 / 0 / 120. Logging 20 minutes with a confirmed 90 remaining produces 120 / 20 / 90; remaining need not equal original minus worked. A remaining-only edit changes neither original nor worked. Replaying the same progress action must not count it twice. Zero remaining must not silently complete the task.

Progress and remaining-only edits require the current **scheduling revision**, so stale submissions cannot overwrite newer work. This is not `board_revision`. Refresh the state and reconsider after a stale conflict; do not automatically retry an old decision with a newer token.

`nominal_workday_minutes` is the effort-conversion setting; `workday_minutes` is a legacy placement-hours setting. Changing the nominal value must not rewrite existing task estimates. Use explicit minutes for this pass; natural-language effort parsing is outside this checklist.

General patch file (`general-test.json`), sent with `theplan availability patch --ref general --file general-test.json`:

```json
{"windows":[{"weekday":0,"start_time":"18:00","duration_minutes":120},{"weekday":2,"start_time":"18:00","duration_minutes":120}]}
```

Weekdays are Monday=0 through Sunday=6. A windows PATCH replaces the policy's window list; it is not an append operation. For restoration, build a writable payload from saved `name` and window fields (`weekday`, `start_time`, `duration_minutes`, `sort_order`), rather than sending the entire GET response.

**Scheduling revision (J-S1-06 path):** Owner SoT is `GET /api/v1/settings` → `UserSettingsOut.scheduling_revision`. CLI: `theplan settings get` puts `scheduling_revision` on the JSON top level beside `ok`; text mode prints it first. Do **not** substitute `board_revision`. Refresh with `settings get` after any scheduling write that bumps the token.

## Reading the results correctly

The scheduling revision tracks relevant active scheduling inputs, not every configuration edit. In S1, nominal minutes and config-only General/shifted Working edits can leave it unchanged. `estimated_duration_minutes` retains the original estimate; use remaining effort for outstanding work. A whole-list policy PATCH can create new window IDs even when restoring identical values.

For the tested API error paths: conflict exits 5; validation/usage exits 1. Other API categories include auth/permission 2, not-found 3, and server/transport 4; inspect the structured error code as well. See [CLI reference](../CLI.md). The sandbox defaults to UTC; choose and record a zone explicitly for later timezone tests.
