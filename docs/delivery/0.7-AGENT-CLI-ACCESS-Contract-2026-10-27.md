## 1. Normative product intent

Operators who want Assist-only can turn off the dedicated agent/CLI channel without losing the web app or built-in Assist. Enforcement is a **server-recognized agent credential** gated by an account setting. The switch cannot stop a program that already holds the user’s browser session, password, or host access; UI and public copy must say so.

---

## 2. Account setting and migration

1. Setting name: **Allow agent and CLI access** (exact label may be tuned in UI copy).
2. **New accounts:** default **off**.
3. **Existing accounts (selected 2026-10-27):** one-time grandfather **on** at migration. Record that the value was grandfathered (audit/migration flag or equivalent) so a later reset-to-product-default is possible without guessing. After migration, the owner may turn it off at any time; turning off applies per §3.6 (agent path only).
4. When **off:** no new agent credential may be issued; every agent-credential request fails with stable code `AGENT_ACCESS_DISABLED` (403) per §3.6. Browser session auth and Assist continue.
5. When **on:** owner may create named, revocable credentials (§3).

---

## 3. Agent credential

1. Table (name flexible): per-user rows with id, label, secret **hash/verifier only**, created_at, last_used_at (nullable), revoked_at (nullable), optional grandfather/migration metadata as needed.
2. Create (browser session only): generate high-entropy secret; return plaintext **once**; store verifier only. Never put the secret in logs, URLs, analytics, or error bodies.
3. List/revoke (browser session only): show label, created, last-used, revoked; revoke sets `revoked_at` (non-null). Effect timing is §3.6 — not “whenever convenient.”
4. Agent credential **must not** call credential-admin routes or change the allow setting.
5. Revoking one credential does not bump `session_epoch` and does not sign out browser sessions. Password change / `session_epoch` bump remains the browser-session revoke path and **must not** be the sole agent-revoke mechanism.

### 3.6 Disable / revoke timing (in-flight and concurrent)

#### Boundary A semantics (chosen — Trish 2026-10-27)

**Chosen:** **A — authorization at the final fresh check** — not commit-order locking. Boundary **B** is not selected; adopting B later is an explicit widen, not a silent upgrade under this choice.

1. **Auth gate** (start of request): fresh DB read of credential row (`revoked_at`), allow-setting, and user disabled flag, with **visibility of previously committed changes** from other sessions (not a stale open-transaction snapshot, not an ORM identity-map hit cached from an earlier statement). Fail closed before handler work if any check fails (precedence below). No process-lifetime cache of “this Bearer is good.”
2. **Final fresh check** (mutating agent requests only): immediately before the durable write unit commits, perform another read with the same **committed-change visibility** requirement. Re-evaluate: `revoked_at` null, allow-setting on, user not disabled. If any fail → abort that write unit (rollback); return the matching agent / account error. Do not commit the write. A same-transaction re-read of a row already loaded earlier in the request does **not** satisfy this unless that read actually observes other sessions’ committed revoke/disable (e.g. appropriate isolation / `SELECT` that sees committed data — not “I still have the object in memory”).
3. **Reads** after a successful auth gate may return data without a second check; that read leakage is accepted under boundary A.

**What this promise is:** Deny when revoke, allow-setting off, or user-disable is **visible as already committed** to the auth gate or final fresh check. It does **not** serialize the gap after that check against a concurrent revoke/disable commit.

**Explicit allowed interleaving (weaker promise — do not paper over):**

1. One or more mutating requests each pass their final fresh check (each sees credential live, setting on, user enabled).
2. Concurrent revoke **and/or** allow-setting off **and/or** user-disable **commits**.
3. Each of those requests may then commit its write.

Every such write’s effect **stands**. No compensating undo. Later requests fail at the auth gate / final check. Multiple in-flight requests already past their final checks can **each** commit after revocation/disable — not a single-write footnote. This window is the product cost of boundary A.

**“Immediate” means:** visible to the next auth gate or final fresh check that observes previously committed changes — not mid-statement cancel after both checks passed, and not a push to in-flight TCP clients.

**Applies equally to:** credential revoke, allow-setting disable, and user disable. The final gate must re-check **all three**, not revoke alone.

**Concurrent requests (same credential):**

- A and B (and further peers) all past final check when revoke commits → each may still commit its write (interleaving above). Ordering after the final check is not a shared lock.
- If revoke is committed **before** a peer’s final check, that peer must abort.
- Two credentials for the same user: revoking credential 1 does not affect credential 2’s gates.

**Error precedence (overlapping conditions on one request, auth gate or final check):**

1. Missing / malformed / unknown Bearer secret → `UNAUTHENTICATED` (do not leak row existence beyond ordinary auth practice).
2. Else credential row has `revoked_at` set → `AGENT_CREDENTIAL_REVOKED` (even if allow-setting is also off).
3. Else allow-setting off → `AGENT_ACCESS_DISABLED`.
4. Else user disabled → existing account-disabled behavior (same code/path as browser for a disabled user; checked again at the final gate on mutating agent requests).

#### Product tradeoff (A recorded; B not selected)

| Boundary | Promise | Cost |
| --- | --- | --- |
| **A — Final fresh check (CHOSEN — Trish 2026-10-27)** | Deny when revoke/disable is visible as committed before the final check; allow TOCTOU between that check and commit | Simpler; no new lock protocol; any number of in-flight requests already past their final checks may each commit after revoke/disable |
| **B — Commit-order protection (not selected)** | Revoke/disable and agent writes share a defined locking/serialization protocol so a write cannot commit after a revoke/disable that committed first | Stronger; needs an explicit protocol (row locks, credential version token checked at commit, etc.) designed and accepted |

**Recorded:** Trish chose **A** (`1793143215.628919`); Dex confirmed/provenance (`1793143239.967159`) — final fresh-check authorization with disclosed multi-request commit-after-revoke/disable. Choosing **B** later remains an explicit widen, not a silent upgrade under A.

Validation: V5, V5b, V5c, V5d, V6 (§6).

## 4. Request authentication

1. Browser path unchanged: signed session cookie + `session_epoch` match via existing `get_current_user`. Today’s cookie payload is **user id + session_epoch only** — no channel / client / “issued-by-CLI” provenance field exists on disk or in the signed session.
2. Agent path: `Authorization: Bearer <secret>` (or equivalent documented header). Resolve to credential → user; require setting on, `revoked_at` null, user not disabled. Codes per §3.6. Cookie alone never satisfies the agent path.
3. Check setting, revocation, and user-disabled on **every** agent request per §3.6; do not rely on cookie TTL or a long-lived self-describing JWT that remains valid after revoke.
4. Spoofed User-Agent / custom headers do not grant agent access and are **not** used to classify cookies.

### 4.1 Legacy CLI cookie vs browser session — what exists and what cutover can enforce

**Provenance today:** None that distinguishes an old CLI-issued cookie from a browser cookie. Both are minted by password → `/api/v1/auth/login` into the same signed session shape (`user_id` + `session_epoch`). The server cannot tell them apart without inventing a client-declared signal (User-Agent, custom header, CLI executable name) — which this design **rejects** as enforcement.

**Cutover enforces (supported channel):**

1. Supported CLI login becomes Bearer credential only — enforced in the **supported CLI client** (it must not call password login). See §5.
2. Agent/CLI **product** gate (allow-setting + revoke) applies only to the Bearer agent path.
3. A leftover CLI cookie file presented as a **cookie** (no Bearer) continues to authenticate only as the **browser** path (same as any stolen/copied browser cookie). It is **not** accepted as proof of agent access.
4. Retiring the supported CLI password flow is **distinct** from blocking programs that possess browser credentials (§1). Phase 1 does not claim to revoke leftover CLI cookie files as a separate class.

**Cutover does not enforce:** selective invalidation of “CLI cookies” while preserving “browser cookies,” because that class distinction does not exist server-side. **Accepted:** Phase 1 cutover does **not** global-bump `session_epoch` (§7) — leftover CLI cookies that remain epoch-valid stay on the **browser** path until normal logout/password/epoch bump. No claim of selective legacy CLI-cookie revocation.

### 4.2 Mixed cookie + Bearer precedence

**Presence rule:** If the request includes an `Authorization: Bearer` agent secret (header present with a Bearer token, including empty/malformed/unknown/revoked/disabled outcomes), the request is classified as an **agent-path attempt**. The signed session cookie must **not** be used as a fallback to authorize the same request.

| Cookie | Bearer | Outcome |
| --- | --- | --- |
| absent / invalid | valid agent credential | Agent path; proceed per §3.6 |
| valid browser session | absent | Browser path (`get_current_user`); not agent |
| valid browser session | present, any Bearer outcome (valid, unknown, revoked, setting off, user disabled) | **Agent path only.** Success only if Bearer passes §3.6. On Bearer denial, return the agent/account error — **never** silently succeed as browser-authorized work |
| absent / invalid | present, denied | Agent/account error only — not a browser login prompt success |

**Credential-admin routes** (create / list / revoke credentials, toggle allow-setting):

1. Require browser session auth.
2. If Bearer is present on the request → **reject** with a stable code (e.g. `AGENT_MIXED_AUTH_REJECTED` or `AGENT_CREDENTIAL_CANNOT_ADMIN`) — do **not** perform admin using the cookie while ignoring/denying Bearer, and do **not** perform admin using Bearer.
3. Agent credentials never call these routes successfully (§3.4); mixed auth does not create a loophole.

**Non-admin routes:** same presence rule — denied Bearer + valid cookie ≠ browser success for that request.

Validation: V11–V13 (§6).

## 5. CLI cutover

1. Supported login: credential-based (`theplan auth login` with token/secret flags — exact UX in impl tip). Persist a session representation that the API recognizes as **agent** auth (Bearer / credential-backed), not a copied browser cookie minted by password login.
2. **Retire CLI password login in the supported CLI client** in the same Phase 1 unlock: the shipped CLI must not call password → `/api/v1/auth/login`; it fails closed locally (or via a dedicated rejected path) with a stable message pointing at the credential path. The **browser** `/api/v1/auth/login` endpoint **remains** for real browser sign-in. That endpoint **cannot** identify arbitrary old CLI callers without provenance (§4.1) and is **not** required to reject password login based on User-Agent or guessed CLI fingerprints.
3. After cutover, unsupported tooling that still posts password login gets a normal browser session cookie if credentials are valid — that is the §1 caveat, not a Phase 1 hole to close via header sniffing. Tooling that sends only an old cookie is on the browser auth path if epoch-valid. Operators who want leftovers dead use logout / password change / ordinary epoch bump — not a cutover-wide bump (§7).
4. Preserve command/JSON/exit-code contract where possible; document any break in the tip.
5. Host-local `auth reset-password` unchanged and explicitly **outside** the allow switch.
