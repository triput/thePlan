## 1. Normative product intent

Operators trigger a **covering refresh**: import and reconcile **local busy cache** for **explicitly selected calendar subscriptions** over an **explicit visible time window**, **without**:

- changing which calendars stay enabled (`PUT …/subscriptions`), or  
- writing remote provider calendars (no export mirror deletes, no subscription metadata writes beyond what §4.1 names), or  
- implying Preview/Apply authorization from a successful subset refresh.

**Covering** (per subscription, on success): provider batch for the effective window fully drained; coverage minted for **`window_effective`** (= operator-visible bounds per §2.2); Google full-window reconcile (immovable rows missing from batch handled per existing full path); Microsoft `calendarView` / `ms_view` path unchanged.

**Legacy route unchanged:** `POST /api/v1/calendar/accounts/{account_id}/sync` retains current semantics (all enabled subs on one account; incremental when Google cursor valid; includes `retry_pending_deletions` and export-side remote DELETE retries). **No** `force_covering` flag on legacy sync.

## 2. API surface (covering-only)

### 2.1 Endpoint

`POST /api/v1/calendar/covering-refresh`

**Auth / ownership:** Same session auth as existing calendar routes.

**Preflight before any provider call:** Full request-shape validation + ownership + eligibility for **every** requested `subscription_id` runs **before** any provider HTTP (including calendar list / identity reads). Ordering:

| Failure class | HTTP | Response shape |
| --- | --- | --- |
| Malformed body, empty/duplicate IDs, window over cap (§2.3), mixed owners in one POST | **422** | Single abort envelope — **no** `results[]` import rows |
| Any requested `subscription_id` missing, foreign, or cross-owner (enumeration risk) | **422** | Single stable code (e.g. `CALENDAR_SUBSCRIPTION_NOT_ELIGIBLE`) — **non-enumerating whole-request abort**; **no** per-target `results[]` row for unknown IDs; **zero** provider HTTP |
| Own-account targets: disabled sub, identity-blocked (T1-F), account disabled/disconnected | **200** | Per-target `results[]` row, `phase=preflight`, terminal eligibility outcome — **not** pulled |

**Never** silently drop IDs from the requested set. **Never** begin provider pull for account A while account B’s ownership is still unverified.

**Body (JSON):**

| Field | Required | Semantics |
| --- | --- | --- |
| `subscription_ids` | yes, non-empty, bounded (see §2.3) | Explicit operator selection; **not** inferred from “all enabled” |
| `window_start`, `window_end` | yes | **Operator-visible range** — timezone-aware instants (ISO-8601); interpreted in UTC after normalization; `end > start` |
| `scheduling_horizon_label` | optional | **Echo-only:** if present, copied into `scheduling_readiness.horizon_label` for client correlation. **Does not** change server horizon computation — readiness always uses `required_coverage_window(settings, now)` (or explicit `horizon.start` / `horizon.end` in response). |

**Forbidden on this route:** `force_covering=false`, `mode=incremental`, or any parameter that selects non-covering ingest. Incremental catch-up remains **only** on legacy account sync.

**Strict request schema:** Unknown top-level or nested fields (including legacy sync knobs such as `mode`, `force_covering`, incremental flags) **must reject** with **422** — **no** silent ignore via OpenAPI extras.

**Response envelope:** HTTP **200** when auth/validation passed and orchestration **finished** per §2.4 (including `partial`, `failed`, and `no_op`). **401/403/422** for auth, validation, whole-request aborts, range/target limits. **502/503** only for pre-orchestration infrastructure faults where **no** per-sub outcome can be persisted honestly (not as a substitute for mixed per-sub provider failure).

**Post-commit / assessment faults:** If durable per-sub commits succeeded but final `scheduling_readiness` assessment or response assembly fails (DB error, timeout), the HTTP response **must not** claim whole-request rollback. Document honestly: **`overall_outcome`** and `results[]` reflect committed import/preflight state; readiness fields may be absent or marked failed; **`action_summary`** remains authoritative for imports. Client must treat partial persistence as possible.

### 2.2 Window policy (frozen — effective = requested; no route pad)

| Concept | Rule |
| --- | --- |
| `window_requested` | Echo `window_start` / `window_end` after validation (operator-visible range) |
| `window_effective` | **Always** identical to `window_requested` (UTC-normalized) — bounds used for provider pull + coverage mint for **this action only** |
| `window_widened` | **`false`** on covering-refresh (frozen) |
| `window_widen_reason` | **`none`** on covering-refresh (frozen) |

**Frozen helper (normative name):** `effective_covering_pull_window(requested_start, requested_end) -> (effective_start, effective_end, widened=false, reason=none)`

| Step | Rule |
| --- | --- |
| 1 | Normalize `requested_*` to UTC; reject `end <= start` (**422**). |
| 2 | Reject requested span **> 42 days** with `CALENDAR_WINDOW_TOO_LARGE` (**422**, whole abort) — **hard cap** on the operator window (§2.3). |
| 3 | **`window_effective = window_requested`** — same basis as legacy `POST …/sync` when **both** `start` and `end` are supplied (explicit range reuse; no silent pad). |
| 4 | **Cursor invalidation (separate):** `coverage_window_wider_than(subscription, required_start=effective_start, required_end=effective_end)` is a **boolean** staleness check only (`rs < stored_start or re > stored_end`). It **does not** compute `window_effective`. |

**Scheduling coverage pad (not pull widening):** `coverage_pad_elapsed(user_settings)` and `required_coverage_window(settings, now)` apply only to **`scheduling_readiness`** / all-enabled freshness evaluation (§5) — **not** to widening `window_effective` on this route.

**Evidence gate (frozen):** If implementation later discovers a **real** provider/cache need to widen explicit pull bounds on covering-refresh, **stop** and return evidence to Dex/Cabinet **before** changing this rule — **no** silent implementation-determined pad branch.

**Worked examples (UTC):**

| Case | Requested | Scheduling horizon (readiness only) | Effective pull | `window_widened` | Notes |
| --- | --- | --- | --- | --- | --- |
| A — narrow UI slice outside horizon | `[now+60d, now+70d]` | `[now, now+42d]` via `required_coverage_window` | Same as requested | `false` | Readiness may be `scheduling_ready=false`; action layer honest about subset window |
| B — explicit week inside horizon | `[now, now+7d]` | wider (includes pad in horizon eval) | Same as requested | `false` | Default path |
| C — over cap | span **> 42d** | n/a | n/a | n/a | **422** before provider pull — no widen-then-fail |

**Freeze:** Response always reports `window_widened=false`, `window_widen_reason=none`. **`scheduling_readiness.horizon`** always comes from `required_coverage_window(settings, now)` — never from `compute_horizon` union with the visible window.

### 2.3 Bounded inputs

| Limit | Contract |
| --- | --- |
| Max span (requested / effective) | `window_end - window_start` ≤ **42 days** — reject over-max with `CALENDAR_WINDOW_TOO_LARGE` (**422**, whole request abort). **`window_effective` equals requested** (§2.2) — single hard cap |
| Max targets | ≤ **20** `subscription_ids` per request |
| Empty / duplicate IDs | 422 |
| Disabled sub (own-account) | Per-target preflight row; **not** pulled |
| Identity-blocked (T1-F) | Per-target preflight row with stable code; **not** pulled |
| Account disabled / disconnected | Per-target preflight row for subs on that account |
| Missing / foreign `subscription_id` | Whole-request **422** abort (§2.1) — **not** a per-target row |

**Import failure rollback:** On provider/import failure for a sub, durable state must match legacy generation semantics: rolled-back cache rows, honest failure sidecar, **no** false `coverage_success_at`. Google covering for targeted subs **invalidates sync cursor** for that sub at refresh start (same as forced full-window path).

**Ownership preflight** completes for **all** targets **before** any provider HTTP on **any** account (OAuth token POST for credentials is allowed; see §3 — **no** provider **calendar mutation** endpoints).

### 2.4 Overall outcome vs per-sub results

| Field | Semantics |
| --- | --- |
| `overall_outcome` | `success` \| `partial` \| `failed` \| `no_op` — **mandatory**; derived from per-sub rows (own-account preflight + import). **422** whole-request aborts do not use this envelope |
| `results[]` | One row per **own-account, known** requested `subscription_id` only (preflight + import). **No** row for missing/foreign IDs (whole abort). |
| `action_summary` | Counts: `requested`, `preflight_rejected`, `import_attempted`, `import_ok`, `import_failed` — **not** a readiness claim |

**Outcome derivation (frozen):** One **`results[]` row per own-account known requested `subscription_id`** (preflight eligibility rows retained). Derive from terminal row status only:

| `overall_outcome` | When |
| --- | --- |
| `no_op` | **Zero** provider import attempts — every requested target terminal at preflight only (disabled, identity-blocked, ineligible after prepare, etc.) |
| `failed` | ≥1 import **attempted** and **zero** `import_ok` among requested targets |
| `success` | **Every** requested target’s terminal row is **`import_ok`** (≥1 import must have been attempted) |
| `partial` | **Not** `success`, **and** ≥1 requested target `import_ok`, **and** ≥1 requested target has preflight rejection **or** import failure |

**Mixed OK:** 200 + `overall_outcome=partial` is normal; client must not treat HTTP status alone as “all calendars fresh.”

## 3. Boundary 1 — Import-cache only (**NEVER** remote calendar writes)

### 3.1 Forbidden side effects on covering-refresh

The covering-refresh path **must not** invoke:

| Seam | Why excluded |
| --- | --- |
| `retry_pending_deletions(… delete_google_event / delete_microsoft_event)` | **Remote DELETE** of provider events (export mirror tombstones) |
| Export / mirror writers | Any code path that creates/updates/deletes provider events for scheduled blocks |
| `PUT …/subscriptions` | Persistent enable/disable selection |
| Subscription-setting mutations beyond §3.2 | Role changes, mirror flags, etc. |

**Required:** A dedicated **`import_covering_subscription_cache`** (name illustrative) entry seam that performs: token read → **subset-filtered** eligible subs → provider **read/list/calendarView** → local upsert/reconcile → coverage mint → failure sidecar — **without** tombstone retry composition.

**Deliberate-delete preservation:** Rows/events suppressed because the operator **verified** intentional remote deletion (Trish Decision, Track 3 policy) remain suppressed via **`suppressed_external_ids` passed into apply** — sourced from **local tombstone state without issuing new provider DELETEs** on this route. Implementation must **read** pending-deletion / suppression sets for import skip logic; it must **not** call `delete_event` on the provider.

### 3.2 Allowed preflight / `prepare_subscriptions_for_sync` effects (named)

`prepare_subscriptions_for_sync` may **read** provider calendar **list** (GET/class read) for identity reconciliation under T1-F account locks — **never** event or calendar **mutation** endpoints.

**Primary bootstrap (frozen):** Legacy `sync_account_events` may call `ensure_primary_subscription` when the account lacks a primary. **Covering-refresh never invokes primary bootstrap** (`ensure_primary_subscription` **forbidden** on this route).

**No-primary accounts (frozen — fixes invented §3.2 rejection):** An account with **no** primary subscription **must not** cause preflight rejection for an **explicitly requested**, **enabled**, **identity-verified** **non-primary** sub. Import **valid requested IDs**; reject **only** actual identity/eligibility uncertainty (T1-F blocked, ambiguous identity, disabled sub, disconnected account, etc.) — **not** “account lacks primary.”

**Identity verification fields (allowed for pull eligibility on requested subs):** provider calendar resource id (`calendar_id` / Graph id), normalized alias keys used by T1-F canonicalization, subscription `role`, `enabled`, and stored identity fingerprint columns — sufficient to resolve **that** sub’s list/read target without mutating roles or expanding the requested set.

**Prepare / canonicalizer subset safety:** `prepare_subscriptions_for_sync` and account-wide canonicalizers **must not** be assumed subset-safe. Covering orchestration runs prepare **only** for **requested** subs on an account; **must not** silently change `CalendarSubscriptionRole`, enable/disable flags, or membership of the POST’s requested set. If prepare would mutate a **non-requested** sub or change role on a requested sub without operator intent, **abort that sub** with explicit preflight code — **never** persist silent role/selection changes.

**Canonical identity mutation (requested sub only):** If prepare **must** rewrite pull identity for a **requested** sub, that mutation commits in the **same owner-locked DB transaction** as any trust/revision side effects from that prepare step (see §4.2). Preserve verified-deletion suppression (`suppressed_external_ids` without new provider DELETEs).

| Effect | Reporting |
| --- | --- |
| Canonicalization changed a requested sub’s pull identity | `results[].preflight_effects[]` includes `canonicalize_identity` |
| Primary bootstrap | **Never** on covering-refresh |
| Sub ineligible after prepare | Explicit preflight rejection — **never** broaden requested subset to “all enabled on account” |

**Provider write boundary:** OAuth token POST ≠ calendar service writes. Covering-refresh orchestration must record **zero** provider calls that mutate calendars or events (no POST/PATCH/DELETE to Graph/Google **calendar/event** resources).

**Tests (mandatory):** Provider HTTP mock records **zero** DELETE/PATCH/POST to event write endpoints; **zero** calls to `delete_google_event` / `delete_microsoft_event` from covering-refresh orchestration (monkeypatch/spy on tombstone retry entrypoint).

## 4. Boundary 2 — Transaction ownership (nested savepoint ≠ per-sub durable commit)

### 4.1 Observed legacy behavior (why contract differs)

Today: `sync_account_events` uses nested savepoints per subscription, but **`sync_calendar_account` commits once** after return. Google/MS loops **raise** on first subscription failure → earlier nested commits may already be **merged into the session** and become durable on outer route commit. Failure sidecars (`_commit_refresh_failure`) may persist even when sibling subs succeeded. **Nested savepoint commit ≠ independent per-sub transaction boundary.**

### 4.2 Required covering-refresh transaction model

| Rule | Requirement |
| --- | --- |
| **Per-sub durable unit** | Each subscription import success/failure must be **independently committed or rolled back** such that a **fresh SQLAlchemy session** read-back sees: success rows **iff** `results[].status=ok`; failed sub **iff** sidecar/failure state with **no** false `coverage_success_at` |
| **Cross-sub failure** | Sub A success **must survive** sub B failure on same account (and cross-account) |
| **Revision atomicity (mandatory)** | Every durable mutation that changes **busy cache**, **trust signature**, **failure-state**, or **identity eligibility** for the owner must commit **required scheduling revision invalidation in the same owner-locked DB transaction** as that mutation — **not** in a later “revision eval” pass after other subs have already committed. Per-sub commits are allowed; **deferred owner revision eval after sub N commits** is **not** (creates committed-new-busy / old-revision window where concurrent Apply or stale Preview can succeed dishonestly). |
| **Revision reporting** | Response reports `scheduling_revision_at_start`, `scheduling_revision_at_end`, and/or `scheduling_revision_bumped` accumulated across the request. **Do not** promise exactly **one** revision bump for the whole multi-commit POST — multiple bumps are valid when multiple owner-locked commit units each change trust. |
| **Final readiness snapshot** | `scheduling_readiness` is computed **once** after all import/preflight terminal state for the POST, under **`lock_owner_scheduling`**, from a **single coherent** owner + revision snapshot. `evaluated_at` is the wall-clock instant of **that** assessment — **not** torn reads from mid-batch commits. |
| **Stale invalidation** | When revision bumps, `scheduling_revision_bumped: true` (or `scheduling_revision_at_end` > `scheduling_revision_at_start`) and **must not** claim `scheduling_ready=true` unless §5 rules satisfied at final snapshot |

**Orchestration commit pattern (normative):** For each subscription target: acquire full lock stack per §7 (reacquired **fresh** per unit) → DB transaction → (optional prepare for **this** sub only) → import covering → **apply revision bump inside same txn if trust/busy changed** → **commit or rollback the unit** (releases **all** transaction-scoped advisory/`FOR UPDATE` locks for that unit) → append `results[]` → release in-process sub lock → next target. **Forbidden:** hold `lock_owner_scheduling` across independent per-sub commits; **Forbidden:** commit sub A import, then bump revision only after sub B; **Forbidden:** compute `scheduling_readiness` from DB state before final owner-locked assessment.

**Failure durable unit (frozen — not exempt from revision atomicity):** After primary import unit **rollback**, releasing txn locks and persisting failure/trust invalidation is **not** exempt from §4.2 revision atomicity or §7 concurrency. Covering-refresh **must** run a **failure durable unit** per failed target that:

1. **Reacquires** the full compatible stack in §7 order (**`lock_calendar_account_for_identity`** when needed → **`lock_owner_scheduling`** → refresh ORM under locks).
2. Re-reads subscription/account row state; **verifies** the failed attempt’s identity fingerprint and **`coverage_active_generation`** have **not** been superseded by a later successful mint, disconnect/delete, disable, or canonical identity change.
3. **Atomically** persists honest failure sidecar / trust invalidation **and** any **required scheduling revision bump** in the **same owner-locked DB transaction**, then commits or rolls back the unit.

**Forbidden:** a late failed attempt overwriting a **later** successful mint, a disconnected/deleted account, or a **newer** identity/generation. **Legacy** `persist_subscription_refresh_failures_autonomous` behavior remains **unchanged** on legacy sync; on covering-refresh, reuse it **only** if it satisfies the failure durable unit above — otherwise implement a **bounded dedicated failure path** for covering (no silent downgrade).

**Token / credential persistence:** OAuth token refresh or credential column writes that must persist before pull run in a **token durable unit** using the **same** account-identity → owner → sub stack (§7) — **never** skip owner/account order. Final **`scheduling_readiness`** snapshot does **not** claim total scheduling authorization (§5).

**Barrier evidence (mandatory tests §9):** Pause **after** first sub’s successful commit **before** starting the next target/finalizer; a **separate session** Apply or stale Preview against pre-request revision must **already reject**. **Separate-session late-failure vs new-success read-back** (V38): after sub A success committed, force sub B failure unit slow-path; concurrent serialized refresh on A must complete; B’s failure durable unit must **not** clobber A’s mint or revision. **Failure-state / revision barrier** (V39): instrument failure unit commit; separate session read-back shows failure sidecar + revision bump **coherent** with owner snapshot — no torn failure without bump when trust invalidates.

**Forbidden evidence claims:** Rolling back a failed sub must **not** leave `results[].status=ok`; success must **not** appear for subs whose coverage mint was rolled back.

## 5. Boundary 3 — Action results ≠ scheduling readiness

### 5.1 Two mandatory report layers

| Layer | Scope | Purpose |
| --- | --- | --- |
| **`coverage_action`** | **Requested** `subscription_ids` only, over `window_effective` | Honest feedback for the operator gesture |
| **`scheduling_readiness`** | **All enabled** subscriptions on owner, over **named scheduling horizon** | Answers “can collect/Apply treat busy as trustworthy for scheduling?” — **not** authorization to Apply |

**Freshness evaluator:** `evaluate_calendar_freshness(db, owner_id, settings, now, required_start=…, required_end=…)` always considers **all enabled** account/sub pairs — **never** a supplied subset only.

**Busy-input trust:** `evaluate_busy_input_trust` for the same scheduling horizon window is **mandatory** in `scheduling_readiness` when the response claims any readiness field. **`busy_input_trust` is not optional** if copy implies scheduling-trustworthy busy.

### 5.2 Readiness shape (timestamped assessment)

```json
"scheduling_readiness": {
  "evaluated_at": "<ISO-8601 UTC>",
  "scheduling_revision": "<int>",
  "horizon": { "start": "...", "end": "..." },
  "freshness_all_enabled": { /* CalendarFreshnessTrust.to_dict() */ },
  "busy_input_trust": { /* same contract as GET …/busy-input-trust */ },
  "scheduling_ready": false,
  "blocking_summary": ["…"]
}
```

| Field | Rule |
| --- | --- |
| `scheduling_ready` | `true` only if `freshness_all_enabled.ok` **and** busy-input trust acceptable for horizon **and** no uncovered **enabled** sub outside requested set still blocks horizon (honest `blocking_summary`) |
| `evaluated_at` | Wall-clock UTC at evaluation instant — **not** Apply authorization |
| Subset success | `coverage_action.all_requested_covering_ok` may be `true` while `scheduling_ready` is **false** (other enabled calendars stale) |

**Uncovered inputs:** Enabled subs **not** in `subscription_ids` remain subject to freshness/trust; response must list them in `blocking_summary` when they block horizon readiness.

## 7. Boundary 5 — Cross-account orchestration (replaces “F6 weak” reuse)

**Prerequisite statement:** Observed F6 proof @ **`8c83c03`** documents **single-account** `sync_account_events` lock/fetch order. **Cross-account subset orchestration with independent per-sub commits is new** — existing F6 test **does not** cover it without extension.

### 7.1 Required orchestration design (implementation phase)

**Observed legacy order (google/microsoft `sync_account_events`):** `lock_owner_scheduling(db, owner_id)` **first**, then per-sub `with subscription_refresh_lock(subscription.id):` around nested import work. T1-F canonicalization uses **calendar-account** advisory/`FOR UPDATE` locks **inside** an open transaction **before** owner lock when identity prepare runs. **Covering-refresh must use a compatible total order** — the **`bbca16c`** draft’s sub-lock-then-owner pattern is **reversed** and **must not** ship (deadlock with legacy sync and with itself under overlap).

**Lock lifetime (frozen — per-sub commit releases txn locks):** Each per-sub durable unit is one **database transaction** (commit or rollback). **`pg_advisory_xact_lock`** and **`FOR UPDATE`** row locks acquired inside that transaction are **released at unit end** — they **cannot** span independently committed subs. **§7 step 7 must not** retain `lock_owner_scheduling` across units. Before **each** unit, reacquire the **full compatible stack** in order below; refresh ORM under those locks (`populate_existing` where applicable); release all txn locks at commit/rollback; release in-process sub lock; repeat. **Final readiness** (step 8) acquires its **own** `lock_owner_scheduling` snapshot — not a continuation of the last import unit.

**Named DB serialization (existing primitives — no vague “add DB protection”):**

| Primitive | Code anchor | Cross-process role |
| --- | --- | --- |

**Failure / disconnect / token paths:** OAuth token refresh or credential column writes that must persist before pull run **inside** a **token durable unit** with the same account-identity → owner → sub stack (§4.2) — **never** skip owner/account order. **Failure durable units** (§4.2) run **after** primary import rollback with **full stack reacquired** — **not** lock-free autonomous sidecars. Disconnect mid-fetch aborts apply under post-fetch re-check — **no** success mint; next unit **reacquires** full stack.

**Frozen lock order (normative trace per subscription unit):**

1. Request preflight (no provider) — §2  
2. OAuth token read/refresh if needed (**no** calendar mutation HTTP) — persistence per paragraph above  
3. **`lock_calendar_account_for_identity`** when T1-F prepare/identity read needed for **this** sub’s account (txn-scoped)  
4. **`lock_owner_scheduling(db, owner_id)`** (txn-scoped — **reacquired every unit**)  
5. **`subscription_refresh_lock(subscription_id)`** (in-process; after DB txn begins or immediately before fetch — **after** steps 3–4 acquired for this unit)  
6. Refresh ORM under locks → optional prepare (**requested** sub only; §3.2) → pre-pull eligibility → provider **read** fetch → **post-fetch** disconnect/disable/identity/generation re-check → cache mutate → revision bump if required → **commit or rollback unit** (releases steps 3–4 txn locks)  
7. Release `subscription_refresh_lock`; on import failure after rollback, run **failure durable unit** (§4.2) with full stack reacquired  
8. Repeat 2–7 for next `subscription_id` (deterministic sort)  
9. Final **`lock_owner_scheduling`** (new txn) + `scheduling_readiness` snapshot (§4.2)

| Concern | Contract |
| --- | --- |
| **`subscription_refresh_lock`** | **In-process only** — same-worker same-sub serialization. Cross-process **same sub** contention relies on **`lock_owner_scheduling`** + generation/apply rules — **not** HTTP 409 from threading. |
| **Concurrent conflicting apply** | **Forbidden:** two in-flight refreshes must not both mint success for the same generation/window. **Allowed:** sequential full refreshes — a **second serialized** request **may** mint after the first completes (V20). **V20 asserts serialization**, not a particular wait site: the second caller **may** block on **`subscription_refresh_lock`** (same process) **or** on **`lock_owner_scheduling`** (separate session/process) — either is valid if no dual conflicting mint. |
| **Disconnect/disable/identity/generation** | Pre-pull check **insufficient**. **Mandatory** post-fetch, pre-apply re-check under step 6. |
| **Provider fetch placement** | Network fetch inside sub lock **after** steps 3–4 for **this** unit; apply/mint only if post-fetch re-check passes. |
| **Multi-owner** | Single POST **single owner**; mixed `owner_id` → **422 abort** (§2) |
| **Deadlock proof** | Disposable tests with **real separate sessions/processes**: legacy vs covering (**same sub** and different sub), covering vs covering **same sub** — all complete without deadlock; same total order on failure/disconnect paths |

**Prerequisite if reuse unsafe:** If independent per-sub commits cannot satisfy §4.2 atomic revision **and** §7 order without violating Microsoft/Google fetch placement, implementation **stops** for Dex decision — **no** silent “F6 weak qual.”
