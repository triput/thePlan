## 1. Normative product intent

Operators trigger a **covering refresh**: import and reconcile **local busy cache** for **explicitly selected calendar subscriptions** over an **explicit visible time window**, **without**:

- changing which calendars stay enabled (`PUT …/subscriptions`), or  
- writing remote provider calendars (no export mirror deletes, no subscription metadata writes beyond what §4.1 names), or  
- implying Preview/Apply authorization from a successful subset refresh.

**Covering** (per subscription, on success): provider batch for the effective window fully drained; coverage minted ⊇ operator-visible bounds (after any documented pad widening); Google full-window reconcile (immovable rows missing from batch handled per existing full path); Microsoft `calendarView` / `ms_view` path unchanged.

**Legacy route unchanged:** `POST /api/v1/calendar/accounts/{account_id}/sync` retains current semantics (all enabled subs on one account; incremental when Google cursor valid; includes `retry_pending_deletions` and export-side remote DELETE retries). **No** `force_covering` flag on legacy sync.

## 2. API surface (covering-only)

### 2.1 Endpoint

`POST /api/v1/calendar/covering-refresh`

**Auth / ownership:** Same session auth as existing calendar routes.

**Preflight before any provider call:** Full request-shape validation + ownership + eligibility for **every** requested `subscription_id` runs **before** any provider HTTP (including calendar list / identity reads). Ordering:

| Failure class | HTTP | Response shape |
| --- | --- | --- |
| Malformed body, empty/duplicate IDs, window over cap (§2.3), mixed owners in one POST | **422** | Single abort envelope — **no** `results[]` import rows |
| Cross-owner or not-found subscription IDs (enumeration risk) | **403** or **422** | Single stable code (e.g. `CALENDAR_SUBSCRIPTION_NOT_ELIGIBLE`) — **non-enumerating abort**; **do not** reveal which foreign IDs exist |
| Own-account targets: disabled sub, identity-blocked (T1-F), account disabled/disconnected | **200** after orchestration **or** early **200** with **only** preflight terminal rows | Per-target `results[]` row, `phase=preflight`, `status=failed` — **not** pulled |

**Never** silently drop IDs from the requested set. **Never** begin provider pull for account A while account B’s ownership is still unverified.

**Body (JSON):**

| Field | Required | Semantics |
| --- | --- | --- |
| `subscription_ids` | yes, non-empty, bounded (see §2.3) | Explicit operator selection; **not** inferred from “all enabled” |
| `window_start`, `window_end` | yes | **Operator-visible range** — timezone-aware instants (ISO-8601); interpreted in UTC after normalization; `end > start` |
| `scheduling_horizon_label` | optional | **Echo-only:** if present, copied into `scheduling_readiness.horizon_label` for client correlation. **Does not** change server horizon computation — readiness always uses `required_coverage_window(settings, now)` (or explicit `horizon.start` / `horizon.end` in response). |

**Forbidden on this route:** `force_covering=false`, `mode=incremental`, or any parameter that selects non-covering ingest. Incremental catch-up remains **only** on legacy account sync.

**Response envelope:** HTTP **200** only when the request passed auth/validation/preflight and orchestration **finished** (success, partial per-sub failure, or zero-success orchestration — see §2.4). **401/403/422** for auth, validation, ineligible targets, range/target limits. **502/503** only for pre-orchestration infrastructure faults where **no** per-sub outcome can be persisted honestly (not as a substitute for mixed per-sub provider failure).

### 2.2 Window policy (no quiet redefinition)

| Concept | Rule |
| --- | --- |
| `window_requested` | Echo `window_start` / `window_end` after validation |
| `window_effective` | Bounds actually used for provider pull + coverage mint for **this action** |
| Pad widening | Allowed **only** when collect/scheduling pad rules require it; must set `window_widened: true`, `window_widen_reason` (enum), and **both** requested and effective bounds |
| **Freeze:** | Pad widening **must not** replace the operator-visible range in UI copy; it supplements pull bounds. **Scheduling-horizon readiness** (§5) uses `required_coverage_window` separately — do **not** silently set “visible range = whole horizon” |

### 2.3 Bounded inputs

| Limit | Contract |
| --- | --- |
| Max span (requested) | `window_end - window_start` ≤ **42 days** — reject over-max with `CALENDAR_WINDOW_TOO_LARGE` (**422**, whole request abort) |
| Max span (effective) | **`window_effective` span** after §2.2 pad widening ≤ **42 days** unless a named server constant documents a higher **effective** cap — if pad would exceed effective cap, **422** abort **before** provider pull (no partial widen-then-fail) |
| Max targets | ≤ **20** `subscription_ids` per request |
| Empty / duplicate IDs | 422 |
| Disabled / missing sub (own-account) | Per-target preflight row; **not** pulled |
| Identity-blocked (T1-F) | Per-target preflight row with stable code; **not** pulled |
| Account disabled / disconnected | Per-target preflight row for subs on that account |

**Pad rule (frozen):** Pad widening uses the **same** collect/scheduling pad helpers as legacy ingest (`coverage_window_wider_than` / horizon compute — no ad-hoc constants). Widening applies to **pull bounds only**; `window_requested` is always echoed unchanged.

**Import failure rollback:** On provider/import failure for a sub, durable state must match legacy generation semantics: rolled-back cache rows, honest failure sidecar, **no** false `coverage_success_at`. Google covering for targeted subs **invalidates sync cursor** for that sub at refresh start (same as forced full-window path).

**Ownership preflight** completes for **all** targets **before** any provider HTTP on **any** account (OAuth token POST for credentials is allowed; see §3 — **no** provider **calendar mutation** endpoints).

### 2.4 Overall outcome vs per-sub results

| Field | Semantics |
| --- | --- |
| `overall_outcome` | `success` \| `partial` \| `failed` \| `no_op` — **mandatory**; derived from per-sub rows (own-account preflight + import). **422 aborts** do not use this envelope |
| `results[]` | One row per **requested** `subscription_id`: preflight failures included with `phase=preflight`; pull failures with `phase=import` |
| `action_summary` | Counts: `requested`, `preflight_rejected`, `import_ok`, `import_failed` — **not** a readiness claim |

**`no_op`:** All requested subs preflight-rejected, or orchestration aborted before any import with zero durable success (document cause).

**Mixed OK:** 200 + `overall_outcome=partial` is normal; client must not treat HTTP status alone as “all calendars fresh.”

## 3. Boundary 1 — Import-cache only (**NEVER** remote calendar writes)

### 3.1 Forbidden side effects on covering-refresh

The covering-refresh path **must not** invoke:

| Seam | Why excluded |
| --- | --- |
| `retry_pending_deletions(… delete_google_event / delete_microsoft_event)` | **Remote DELETE** of provider events (export mirror tombstones) |
| Export / mirror writers | Any code path that creates/updates/deletes provider events for scheduled blocks |
| `PUT …/subscriptions` | Persistent enable/disable selection |
| Subscription-setting mutations beyond §3.2 | Role changes, mirror flags, etc. |

**Required:** A dedicated **`import_covering_subscription_cache`** (name illustrative) entry seam that performs: token read → **subset-filtered** eligible subs → provider **read/list/calendarView** → local upsert/reconcile → coverage mint → failure sidecar — **without** tombstone retry composition.

**Deliberate-delete preservation:** Rows/events suppressed because the operator **verified** intentional remote deletion (Trish Decision, Track 3 policy) remain suppressed via **`suppressed_external_ids` passed into apply** — sourced from **local tombstone state without issuing new provider DELETEs** on this route. Implementation must **read** pending-deletion / suppression sets for import skip logic; it must **not** call `delete_event` on the provider.

### 3.2 Allowed preflight / `prepare_subscriptions_for_sync` effects (named)

`prepare_subscriptions_for_sync` may **read** provider calendar **list** (GET/class read) for identity reconciliation under T1-F account locks — **never** event or calendar **mutation** endpoints.

**Primary bootstrap (frozen):** Legacy `sync_account_events` may call `ensure_primary_subscription` when the account lacks a primary. **Covering-refresh with explicit `subscription_ids` omits primary bootstrap entirely.** If the account has no primary and the operator did not list a resolvable primary sub, affected account targets return **preflight ineligible** — **no** persistent selection/role changes on this route.

**Canonical identity mutation:** If prepare **must** rewrite pull identity for a **requested** sub, that mutation commits in the **same owner-locked DB transaction** as any trust/revision side effects from that prepare step (see §4.2). Preserve verified-deletion suppression (`suppressed_external_ids` without new provider DELETEs).

| Effect | Reporting |
| --- | --- |
| Canonicalization changed a requested sub’s pull identity | `results[].preflight_effects[]` includes `canonicalize_identity` |
| Primary bootstrap | **Not invoked** on covering-refresh — if legacy would have bootstrapped, return preflight ineligible instead |
| Sub ineligible after prepare | Explicit preflight rejection — **never** broaden requested subset to “all enabled on account” |

**Provider write boundary:** OAuth token POST ≠ calendar service writes. Covering-refresh orchestration must record **zero** provider calls that mutate calendars or events (no POST/PATCH/DELETE to Graph/Google **calendar/event** resources).

**Tests (mandatory):** Provider HTTP mock records **zero** DELETE/PATCH/POST to event write endpoints; **zero** calls to `delete_google_event` / `delete_microsoft_event` from covering-refresh orchestration (monkeypatch/spy on tombstone retry entrypoint).

## 4. Boundary 2 — Transaction ownership (nested savepoint ≠ per-sub durable commit)

### 4.1 Observed legacy behavior (why contract differs)

Today: `sync_account_events` uses nested savepoints per subscription, but **`sync_calendar_account` commits once** after return. Google/MS loops **raise** on first subscription failure → earlier nested commits may already be **merged into the session** and become durable on outer route commit. Failure sidecars (`_commit_refresh_failure`) may persist even when sibling subs succeeded. **Nested savepoint commit ≠ independent per-sub transaction boundary.**

### 4.2 Required covering-refresh transaction model

| Rule | Requirement |
| --- | --- |
| **Per-sub durable unit** | Each subscription import success/failure must be **independently committed or rolled back** such that a **fresh SQLAlchemy session** read-back sees: success rows **iff** `results[].status=ok`; failed sub **iff** sidecar/failure state with **no** false `coverage_success_at` |
| **Cross-sub failure** | Sub A success **must survive** sub B failure on same account (and cross-account) |
| **Revision atomicity (mandatory)** | Every durable mutation that changes **busy cache**, **trust signature**, **failure-state**, or **identity eligibility** for the owner must commit **required scheduling revision invalidation in the same owner-locked DB transaction** as that mutation — **not** in a later “revision eval” pass after other subs have already committed. Per-sub commits are allowed; **deferred owner revision eval after sub N commits** is **not** (creates committed-new-busy / old-revision window where concurrent Apply or stale Preview can succeed dishonestly). |
| **Revision reporting** | Response reports `scheduling_revision_at_start`, `scheduling_revision_at_end`, and/or `scheduling_revision_bumped` accumulated across the request. **Do not** promise exactly **one** revision bump for the whole multi-commit POST — multiple bumps are valid when multiple owner-locked commit units each change trust. |
| **Final readiness snapshot** | `scheduling_readiness` is computed **once** after all import/preflight terminal state for the POST, under **`lock_owner_scheduling`**, from a **single coherent** owner + revision snapshot. `evaluated_at` is the wall-clock instant of **that** assessment — **not** torn reads from mid-batch commits. |
| **Stale invalidation** | When revision bumps, `scheduling_revision_bumped: true` (or `scheduling_revision_at_end` > `scheduling_revision_at_start`) and **must not** claim `scheduling_ready=true` unless §5 rules satisfied at final snapshot |

**Orchestration commit pattern (normative):** For each subscription target: acquire locks per §7 → owner-locked DB transaction → (optional prepare effects for **this** sub only) → import covering → **apply revision bump inside same txn if trust/busy changed** → commit **or** rollback → append `results[]` → release sub lock → next target. **Forbidden:** commit sub A import, then bump revision only after sub B; **Forbidden:** compute `scheduling_readiness` from DB state before final owner-locked assessment.

**Barrier evidence (mandatory tests §9):** Pause **after** first sub’s successful commit **before** starting the next target/finalizer; a **separate session** Apply or stale Preview against pre-request revision must **already reject**. Interrupted-request read-back must not expose torn busy vs revision.

**Forbidden evidence claims:** Rolling back a failed sub must **not** leave `results[].status=ok`; success must **not** appear for subs whose coverage mint was rolled back.

## 5. Boundary 3 — Action results ≠ scheduling readiness

### 5.1 Two mandatory report layers

| Layer | Scope | Purpose |
| --- | --- | --- |
| **`coverage_action`** | **Requested** `subscription_ids` only, over `window_effective` | Honest feedback for the operator gesture |
| **`scheduling_readiness`** | **All enabled** subscriptions on owner, over **named scheduling horizon** | Answers “can collect/Apply treat busy as trustworthy for scheduling?” — **not** authorization to Apply |

**Freshness evaluator:** `evaluate_calendar_freshness(db, owner_id, settings, now, required_start=…, required_end=…)` always considers **all enabled** account/sub pairs — **never** a supplied subset only.

**Busy-input trust:** `evaluate_busy_input_trust` for the same scheduling horizon window is **mandatory** in `scheduling_readiness` when the response claims any readiness field. **`busy_input_trust` is not optional** if copy implies scheduling-trustworthy busy.

### 5.2 Readiness shape (timestamped assessment)

```json
"scheduling_readiness": {
  "evaluated_at": "<ISO-8601 UTC>",
  "scheduling_revision": "<int>",
  "horizon": { "start": "...", "end": "..." },
  "freshness_all_enabled": { /* CalendarFreshnessTrust.to_dict() */ },
  "busy_input_trust": { /* same contract as GET …/busy-input-trust */ },
  "scheduling_ready": false,
  "blocking_summary": ["…"]
}
```

| Field | Rule |
| --- | --- |
| `scheduling_ready` | `true` only if `freshness_all_enabled.ok` **and** busy-input trust acceptable for horizon **and** no uncovered **enabled** sub outside requested set still blocks horizon (honest `blocking_summary`) |
| `evaluated_at` | Wall-clock UTC at evaluation instant — **not** Apply authorization |
| Subset success | `coverage_action.all_requested_covering_ok` may be `true` while `scheduling_ready` is **false** (other enabled calendars stale) |

**Uncovered inputs:** Enabled subs **not** in `subscription_ids` remain subject to freshness/trust; response must list them in `blocking_summary` when they block horizon readiness.

## 7. Boundary 5 — Cross-account orchestration (replaces “F6 weak” reuse)

**Prerequisite statement:** Observed F6 proof @ **`8c83c03`** documents **single-account** `sync_account_events` lock/fetch order. **Cross-account subset orchestration with independent per-sub commits is new** — existing F6 test **does not** cover it without extension.

### 7.1 Required orchestration design (implementation phase)

**Observed legacy order (google/microsoft `sync_account_events`):** `lock_owner_scheduling(db, owner_id)` **first**, then per-sub `with subscription_refresh_lock(subscription.id):` around nested import work. T1-F canonicalization uses **calendar-account** advisory/`FOR UPDATE` locks **inside** an open transaction **before** owner lock when identity prepare runs. **Covering-refresh must use a compatible total order** — the **`bbca16c`** draft’s sub-lock-then-owner pattern is **reversed** and **must not** ship (deadlock with legacy sync and with itself under overlap).

**Frozen lock order (normative trace):**

1. Request preflight (no provider) — §2  
2. Per account (single owner per POST): OAuth token if needed (no calendar mutations)  
3. Optional T1-F prepare for **requested** subs only — **calendar-account lock → FOR UPDATE account → reads**; **no** primary bootstrap (§3.2)  
4. **`lock_owner_scheduling(db, owner_id)`** — held across each owner-locked commit unit that mutates busy/trust/revision  
5. Per targeted sub (deterministic sort by `subscription_id`): **`subscription_refresh_lock(subscription_id)`** (in-process **blocking** `threading.Lock` — **not** try-lock, **not** HTTP 409)  
6. DB transaction: re-check eligibility → provider **read** fetch → **re-check** disconnect/disable/identity/generation **again after fetch, before apply** → cache mutate → revision bump if required → commit  
7. Release sub lock; repeat 5–6; release owner scheduling lock when no further owner-locked commits pending for this POST  
8. Final **`lock_owner_scheduling`** + `scheduling_readiness` snapshot (§4.2)

| Concern | Contract |
| --- | --- |
| **`subscription_refresh_lock`** | **In-process only** — second thread blocks until the first refresh completes. **Not** cross-process mutual exclusion. Where multi-process refresh is possible, add **DB-level** protection (generation/row locks already in refresh start) — do not rely on 409 from threading lock. |
| **Disconnect/disable/identity/generation** | Pre-pull check **insufficient**. **Mandatory** post-fetch, pre-apply re-check under §7 step 6 write path. |
| **Provider fetch placement** | Network fetch occurs **inside** sub refresh lock **after** owner lock acquired for that commit unit; apply/mint only if post-fetch re-check passes. |
| **Multi-owner** | Single POST **single owner**; mixed `owner_id` → **422 abort** (§2) |
| **Deadlock proof** | Disposable tests with **real separate sessions**: covering vs legacy sync overlap; covering vs covering overlap — both must complete without deadlock |

**Prerequisite if reuse unsafe:** If independent per-sub commits cannot satisfy §4.2 atomic revision **and** §7 order without violating Microsoft/Google fetch placement, implementation **stops** for Dex decision — **no** silent “F6 weak qual.”

**Clock-slide:** Remains **separately open** (Track 1). Response uses real `now` for freshness; **does not** claim automatic preview invalidation on wall-clock slide.
