## 5. Contract (restated from authority — not new product)

From SPEC §4.2–§4.4 / Dex redesign review / cutover **A14b** / **A14c** — already approved language; V4b implements the **deferred** layer on top of live V4 composition:

**Day-scoped (SPEC §4.3):**

1. **Change selected days** — replaces the targeted inherited window on selected days/dates only; outside that scope the rule does not participate; normal inheritance continues; independent requirements and busy still apply. Offer one specific date or recurring weekday; one-date changes expire to underlying schedule. Replacement removes the original window for that scope — does not silently add an alternative alongside it.
2. **Only allow selected days/times** — hard eligibility; outside those days/times automatic placement needs an explicit scoped exception. Active required rule with explicitly no permitted time → no eligible time; **no** ancestor fall-through. Deadline / high priority does **not** silently weaken exclusive.
3. Empty replacement closes targeted availability without fall-through; expiry/removal restores underlying (preview that consequence).

**Dated exceptions / overlap (SPEC §4.4):**

1. Exceptions target a rule and scope (task, date range, or standing-rule change): add / replace named / waive named — **no** ignore-all.
2. Resolve authorized scoped exceptions into effective inputs **before** the May/Must/Prefer stack.
3. Temporary exceptions expire into recurring baseline.
4. Overlapping dated availability: never save-order or implicit shortest-range-wins; explicit which-replaces-which; unresolved → atomic reject, draft preserved, saved unchanged.

**Ranking protection (SPEC §4.2 normal ranking / A14c):**

1. Preserve existing task priority/deadline ordering; preferences choose among eligible placements.
2. Preference must not cause an **avoidable** deadline miss — use eligible afternoon fallback when preferred evenings cannot meet the deadline.
3. When both placements meet the deadline, favor preferred window if that does not prevent a higher-ranked task from being placed.
4. Hard requirements and pins stay protected; explain unmet preferences. Bounded behavior in the existing scheduler — not a global optimum promise.

**V4 handoff:** Standing composition + bounded Prefer live; dated/weekday/expiry/full ranking-protection deferred here.

### 12.4 Prefer rank today vs what A14c would consult

Prefer rank-only is **inside one task’s day**, after eligibility exists. It does not look at other tasks.

| Piece | Where | What it does |
| --- | --- | --- |
| Rank order | `composition_search_windows` | Builds the eligible set (May ∪ then Must ∩), intersects Prefer windows with it, returns `(start, end, RANK_PREFER)` then `(start, end, RANK_ELIGIBLE)`. Prefer adds no span. |
| Walk | `place_task` | For a new-rule task, walks those windows in that order. `find_slot` takes the first fit. Time-map tier is forced `None` on this branch (`window_tier = None if composition_active`). Green/yellow/neutral stay on the legacy `_day_search_windows` path. |
| Deadline clip | `find_slot` | Search start at or after `deadline` → no slot. Slot end past `deadline` → skip. A Prefer window that cannot fit before `task.deadline_at` is skipped; the walk continues into later windows, including `RANK_ELIGIBLE`. That is the bounded within-task fallback (afternoon eligible after an evening Prefer that misses the deadline). It is not a cross-task check. |
| Unmet preference | `place_task` → `calculate.py` → `reasons.py` | If any block lands on a non-`RANK_PREFER` window while `prefer_rules` is non-empty, `unmet_preference = {prefer_rule_ids, placed_outside_preferred_window: True}`. Copy: `REASON_UNMET_PREFERENCE`. |
| Task order | `calculate.py` `_placement_pass_order` | Ready tasks sorted by `_PRIORITY_RANK` (priority), then higher UPS, then topo index. Each call is `place_one_block` → `place_task`, which **greedily keeps the first Prefer slot `find_slot` accepts**. No later pass reopens that Prefer-vs-eligible choice. |
| UPS clock | `scheduler/ups.py` | Score input is the first of `deadline_at`, `soft_target_at`, `due_at`. Ordering weight only. Not a Prefer constraint. |
| Pins / hard busy | `find_slot` + `expand_fixed_busy_for_placement` | Pins and external events already block placement. Prefer does not move them. |

**What A14c would have to consult (no algorithm invented):**

- This task’s `deadline_at`, already a hard clip inside `find_slot`, and already the `deadline` fingerprint category.
- This task’s Prefer-vs-eligible window list from `composition_search_windows` (the choice bounded A14 already makes by walk order).
- Other tasks’ priority (`_PRIORITY_RANK` / `task.priority`), UPS (`ups_scores`), and whether they are not yet placed because a dependency sweep has not reached them (`_dependencies_ready`, `_prerequisite_not_before`).
- Busy already taken by earlier placements in the sweep, plus pins.
- The existing unmet-preference fact, if the protection places outside Prefer on purpose.

There is **no** symbol that asks “does taking this Prefer slot cause an avoidable deadline miss for me, or block a higher-ranked task that is not placed yet?” Bounded A14 proved the within-task walk (Prefer first, eligible fallback, explain unmet). Full A14c is that missing consult. Do not specify the consult’s decision rule in this map. Do not treat `_placement_pass_order` as that rule: it orders **who is placed next**, and the placed task still takes Prefer if `find_slot` can.
