## 1. Product intent (paraphrase — confirm against Cabinet §IX)

Operators need a deliberate **covering refresh**: pull and reconcile external busy for **chosen calendar subscriptions** over an **explicit time window** (the range they care about on screen or for the next scheduling action), **without** conflating that action with:

- editing which calendars are enabled (`PUT …/subscriptions`), or  
- incidental provider **incremental** deltas that do not prove full-window coverage (T1-12 qual: incremental omit can leave legacy null/free-busy unresolved until a covering fetch returns).

After refresh, the product must report **honest readiness**: per-calendar coverage/failure/stale state and busy-input trust for the requested window — not a silent “sync succeeded” when freshness or trust still blocks collect/Apply.

Decision 2 is a **safe-usable milestone** input (criteria reconcile §1.3). It is **not** a D3 substitute and **not** unlocked by the D3 local-close stamp.

## 3. Smallest bounded contract (proposal — Dex review before code)

**Goal:** One disposable-testable **API surface** that composes existing ingest + existing evaluators — **no** new provider protocol, **no** household migrate, **no** Apply/Preview authorization, **no** live Graph.

### 3.1 Suggested endpoint shape (minimal)

Prefer **extending** the existing sync route with explicit semantics over a parallel pipeline:

`POST /api/v1/calendar/covering-refresh`

**Body (JSON):**

| Field | Required | Semantics |
| --- | --- | --- |
| `subscription_ids` | yes (non-empty) | Subset of **enabled** subscriptions the operator selected (UUIDs); server rejects disabled / other-owner / identity-blocked (T1-F) |
| `window_start`, `window_end` | yes | UTC instants; `end > start`; server may **widen** to minimum pad rules (`coverage_pad_elapsed` / collect gate) and document widening in response |
| `force_covering` | default `true` for this route | **Google:** invalidate incremental cursor for those subs and run **full** window pull + in-window stale reconcile. **Microsoft:** ordinary calendarView (already covering). **Product choice:** whether generic account `sync` stays incremental-only |

**Response (JSON):**

| Field | Semantics |
| --- | --- |
| `window_requested` / `window_effective` | Honest bounds after pad widening |
| `results[]` | Per `subscription_id`: `status` (`ok` \| `error`), `upserted`, `provider`, optional `error_code` / `failure_cause` |
| `freshness` | `CalendarFreshnessTrust.to_dict()` evaluated at **`now`** for `window_effective` (subset-aware: only requested subs, or all enabled — **product choice §4**) |
| `busy_input_trust` | Optional: same window via `evaluate_busy_input_trust` (read-only mirror of busy-input-trust route) |
| `scheduling_revision_bumped` | bool — surfaced so UI can mention Preview stale (Boundary B alignment) |

**Implementation note (Justin/Tesla consult):** Internally group `subscription_ids` by `calendar_account_id` and call existing `sync_account_events` **or** extract a package-private `sync_account_subscriptions(..., subscription_filter, force_covering=True)` to avoid duplicating lock/coverage/revision logic. **Do not** reorder locks in the first slice (F6 qual).

### 3.2 Behavior definitions

**Covering refresh (normative):** For each targeted subscription, after success:

1. Provider batch for `[window_effective]` fully drained (`pagination_complete`).  
2. Coverage minted with `coverage_window_start/end` ⊇ requested window (after widening).  
3. **Google:** immovable events intersecting window but absent from provider batch removed (full reconcile) or soft-cancel per existing rules.  
4. **Microsoft:** immovable rows missing from batch **soft-cancelled** in window (`ms_view` path).  
5. `coverage_success_at` fresh; generation aligned.

**Incremental (explicitly out of scope for this route):** Provider delta / syncToken path that updates changed rows **without** proving window-complete batch. Remains available via existing account `sync` when `force_covering=false` **if** Dex wants both modes; otherwise keep incremental on legacy route only.

### 3.3 Partial / error outcomes

| Scenario | Proposed contract |
| --- | --- |
| Single sub provider failure | Record `calendar_refresh_failed` (existing sidecar); **do not** mint success for that sub; include in `results[]` |
| Other subs on same account | **Product choice §4:** (A) all-or-nothing account transaction vs (B) best-effort per sub with independent commits |
| Auth failure before pull | Pre-pull failure path (existing) for all targeted subs on that account |
| Pagination incomplete | Fail that sub with `calendar_pagination_incomplete`; no partial mint |
| T1-F identity-blocked sub | Exclude with explicit `error_code` (do not silently skip) |
| HTTP 502 to client | Only when **zero** subs succeed? or always 200 with mixed `results`? — **product choice §4** |

**Recommendation:** **200 + mixed `results`** for operator honesty (matches “report readiness even when partial”); collect/Apply remain fail-closed via existing gates.

### 3.4 Stale / owner-lock interactions

| Mechanism | Behavior today | D2 contract should |
| --- | --- | --- |
| `lock_owner_scheduling` | Taken before cache mutation (Google: before per-sub loop; MS: after pre-lock fetch) | Document **observed** order; **no F6 rewrite** in D2 slice |
| `subscription_refresh_lock` | Serializes in-process refresh per sub | Surface “refresh already running” as retryable error (if detectable) or block until complete |
| Freshness age ceiling | 15 minutes (`FRESHNESS_AGE_CEILING`) | Post-refresh `freshness.ok` reflects new `coverage_success_at` |
| Clock slide | Horizon / stale coverage without sync | Response uses **real `now`** for freshness (Boundary B class); **does not** claim clock-slide preview invalidation |
| Preview stale | Sync may bump revision when trust/busy changes | Expose `scheduling_revision_bumped`; **do not** auto-replan |
