## 2. What date-first release already does vs what recovery would add

### Release already accomplishes (R-retry)

- Operator reviews / sets **usable dates** (PATCH then POST release, or atomic bounds on release).
- Preserves disposition id / episode_key / snapshot history of the miss.
- Clears held → task is again schedulable under reviewed bounds.
- Temporal gate only (`BOUNDS_STILL_MISSED` + nested savepoint rollback). Free-slot / horizon is ordinary calculate after release — not a release concern.

### When recovery adds nothing

| Case | Why release (or leave/skip) is enough |
| --- | --- |
| One-off / stand-in with no series | Catch-up *is* retrying the same live task |
| Intent is retry-same-task under new dates | That is exactly R-retry |
| Skip forever | `skip_held` — no catch-up wanted |
| Leave-held only | Operator not ready; no new identity needed |
| Post-release no-slot / horizon miss | Ordinary calculate/place — not a new disposition kind |

### When recovery would genuinely differ

| Case | Why release alone is insufficient |
| --- | --- |
| **(1) Recurring — catch-up beside next normal** | Release retargets the **single** live task. Catch-up that must **coexist** with the next normal occurrence without merging identities needs a distinct authored one-off. |
| **(2) After S-suppress** | Skip is task-wide; dates do not un-skip. Reactivation path is not release. |
| **(3) Preserve miss as history while catch-up is separate** | Want miss row to stay historical while a new one-off carries the catch-up — without rewriting series dates via release. |

**Code today:** no recovery resolution, event, route, or service.

## 3. One missed-occurrence example (end-to-end)

**Clock:** Tesla narrative **`FIXED_NOW = 2026-08-11 12:00 UTC`**.

### Primary — recurring (recovery would differ)

| Step | Narrative |
| --- | --- |
| **Source / miss** | Recurring task **“Weekly books”** — live occurrence window Mon 2026-08-11 09:00–11:00 UTC, deadline before noon. At FIXED_NOW the window is past → engine records held miss (`task_occurrence_dispositions`; `episode_key` from bounds+deadline; immutable `bounds_snapshot`). Task stays need-decision; **not** completed; **not** silently stacked into Tue. |
| **Next normal** | Series next-normal remains the following week’s occurrence (e.g. Mon 2026-08-18), advanced only when an occurrence is **completed** (`complete_task` → `next_due_at`). Release/skip do not advance it. |
| **If operator uses date-first release only** | Clears the held row (`released`), patches live task bounds to a reviewed usable window (e.g. Wed 2026-08-13 afternoon). Live task is now “this week’s catch-up” **and** still the series vehicle — **merge risk**: the catch-up and the Aug-18 normal are not distinct identities. |
| **Proposed recovery identity (recommendation — not impl)** | Reviewed **one-off catch-up** distinct from the live series task: e.g. one-off “Weekly books — catch-up (missed 2026-08-11)” with operator-chosen usable dates (Wed 2026-08-13 14:00–16:00 UTC). Miss disposition stays terminal historical (or explicitly linked); series live task continues toward **next normal** Aug-18 without having its dates rewritten into the catch-up. |
| **Preserved history / progress** | Held miss evidence (`miss_detected`, snapshot, episode_key) remains auditable. Logged progress on the series task (if any under P0) is not silently transferred unless product later says so — WAIT product. |
| **Relation to next normal** | Catch-up one-off **coexists** with Aug-18 normal. Completing catch-up does not complete the series occurrence; completing Aug-18 advances `next_due_at` as today. |
| **What Trish reviews / chooses** | (a) leave-held · (b) skip · (c) **release** same-task under new dates · **or** (d) **authorize recovery one-off** with reviewed dates — knowing (d) is the only path that keeps catch-up beside next-normal without merge. No automatic backlog; no silent second row. |

### Short note — one-off (release sufficient)

Same clock, **non-recurring** “File Q2 receipts” missed 09:00–11:00. Intent is retry the same task under Wed afternoon dates → **date-first release**. Recovery adds nothing; inventing a second identity would be busywork.
