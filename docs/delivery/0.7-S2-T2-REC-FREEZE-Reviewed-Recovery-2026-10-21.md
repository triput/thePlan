## 1. Today’s series transition (code-backed) vs proposed

### Today — how next normal is reached

**One-liner:** Next normal is **not** reached on leave / release / skip / scheduler; only `complete_task` overwrites the single `Task.due_at` via `next_due_at` (or a human PATCHes `due_at`).

| Fact | Code path |
| --- | --- |
| Sole RRULE advance | `POST /tasks/{id}/complete` → `complete_task` (`task_helpers.py`) → `recurrence.next_due_at` → `task.due_at = nxt`; task stays open. Board `done` → `transition_task_workflow` → same `complete_task`. |
| What `next_due_at` is | Function in `recurrence.py`, not a stored “next normal” row. Zone = `RecurrenceRule.timezone` (IANA). Clock from previous due’s local h/m/s (else 09:00). |
| Fixed vs completion-anchored | **`is_fixed=true`:** first RRULE instant **strictly after `previous_due`** — steps **once**, even into the past (multi-week miss does **not** catch up to next future). **`is_fixed=false`:** first instant **strictly after `completed_at`** — intermediate missed slots are skipped. |
| What complete does **not** do | Does **not** touch `worked_minutes`, `remaining_minutes`, `estimated_duration_minutes`, `deadline_at`, `start_no_earlier_at`, `start_no_later_at`, blocks, or reminders. **Bounds do not roll** on complete today. |
| Schema | One `Task` + optional one `recurrence_rules` row. **No occurrence table.** Held miss = `task_occurrence_dispositions` only. Progress ledger = append-only `task_progress_entries` keyed by `task_id` (no episode_key). |
| Held insert | `stage_auto_misses` writes `unresolved_held`; does **not** move `due_at` / bounds / completion / effort. |
| While held | `calculate` skips placement for that `task_id`. Leave-held = event only. |
| `release_held` | Clears hold; optional live **bounds** patch; **no** `due_at`, **no** `next_due_at`, **no** `complete_task`, **no** effort reset. |
| `skip_held` | `resolution=skipped`; **no** date writes; task stays skipped for placement. |
| Scheduler | `apps/api/app/scheduler/` does not import recurrence; **no** advance-without-complete tick. |
| Manual escape | `PATCH` task may set `due_at` by hand — not an RRULE step; effort columns unchanged. |

**Honesty:** Completing a held miss to “get to next week” **is** false-completing that missed work from a product view: the system advances the series by treating the occurrence as completed, **and** leaves miss-era live `worked_minutes` / `remaining_minutes` on the same row so next-normal inherits contamination. Leave/release/skip leave the live task stuck on the missed occurrence.

**Do not claim:** next-normal coexistence with an unrecovered miss is already supported. It is not. Bounds roll on complete is not supported today either.

### Proposed — only if recovery ships (not implemented)

Recovery would add a **new** path that:

1. Authors a **distinct one-off** for the missed episode (catch-up identity) with its own effort init.
2. Snapshots miss-era progress attribution onto the disposition (or linked record) **before** mutating live series columns.
3. Advances the **series** pointer (`due_at` + occurrence bounds/deadline roll in source zone — see §5.1) to the next RRULE instant **without** calling `complete_task` on the miss.
4. Resets **live** series effort columns for next-normal (see §6) while leaving the append-only ledger on the series `task_id`.
5. Clears or terminals the task-wide hold so the series task is schedulable for next-normal.
6. Ensures completing the catch-up one-off does **not** invoke the series task’s `complete_task`.

Until that path exists, “catch-up beside next-normal” is **proposed product**, not current behavior.

## 3. Release vs recovery (unchanged honesty)

### Release already accomplishes (R-retry)

- Operator reviews / sets **usable dates** (PATCH then POST release, or atomic bounds on release).
- Preserves disposition id / episode_key / snapshot history of the miss.
- Clears held → task is again schedulable under reviewed bounds.
- Temporal gate only (`BOUNDS_STILL_MISSED` + nested savepoint rollback). Free-slot / horizon is ordinary calculate after release — not a release concern.
- **Does not** create a second identity; **does not** advance `due_at` / RRULE; **does not** reset effort.

### When recovery adds nothing

| Case | Why release (or leave/skip) is enough |
| --- | --- |
| One-off / stand-in with no series | Catch-up *is* retrying the same live task |
| Intent is retry-same-task under new dates | That is exactly R-retry |
| Skip forever | `skip_held` — no catch-up wanted |
| Leave-held only | Operator not ready; no new identity needed |
| Post-release no-slot / horizon miss | Ordinary calculate/place — not a new disposition kind |

### When recovery would genuinely differ

| Case | Why release alone is insufficient |
| --- | --- |
| **Recurring — catch-up beside next normal** | Release retargets the **single** live task. Catch-up that must **coexist** with next-normal needs a distinct authored one-off **plus** a series advance that is not `complete_task` on the miss **plus** live effort reset so next-normal is not contaminated. **None of that exists today.** |
| **After S-suppress** | Skip is task-wide; dates do not un-skip. Reactivation path is not release. **Separate later question — not in min useful scope.** |
| **Preserve miss as history while catch-up is separate** | Want miss row historical while a new one-off carries catch-up — without rewriting series dates via release alone. Covered by the recurring min scope when that ships. |

**Code today:** no recovery resolution, event, route, or service.

## 4. Corrected Tuesday example (end-to-end) — quantitative 60 / 25

**Clock:** Tesla narrative **`FIXED_NOW = 2026-08-11 12:00 UTC`**.  
**Calendar:** **2026-08-11 and 2026-08-18 are Tuesdays** (not Mondays).  
**Effort fixture:** original estimate / occurrence effort = **60 minutes**; miss-era logged = **25 minutes**; remaining at miss detection = **35** (client-supplied remaining on last progress POST — server does **not** derive `original − worked`).

### Primary — recurring (recovery would differ; coexistence is proposed only)

| Step | Narrative |
| --- | --- |
| **Source / miss** | Recurring task **“Weekly books”** — live occurrence window **Tue** 2026-08-11 09:00–11:00 UTC, deadline before noon. Estimate **60**. Operator logged **25** before the window expired → `worked_minutes=25`, `remaining_minutes=35`, ledger has progress entry(ies) totaling 25. At FIXED_NOW the window is past → engine records held miss (`task_occurrence_dispositions`; `episode_key` from bounds+deadline; immutable `bounds_snapshot`). Task stays need-decision; **not** completed; **not** silently stacked into Wed. |
| **Next normal today** | Series does **not** move to **Tue** 2026-08-18 on its own. Leave / release / skip / scheduler leave `due_at` on the missed occurrence. Operator reaches Aug-18 only by **`complete_task`** (false-completes the miss; **leaves** live `worked=25` / `remaining=35`) or by **manual `due_at` PATCH** (same effort contamination). |
| **If operator uses date-first release only** | Clears the held row (`released`), patches live task bounds to a reviewed usable window (e.g. Wed 2026-08-13 afternoon). Live task is now “this week’s catch-up” **and** still the series vehicle — **merge risk**: catch-up and Aug-18 normal are not distinct identities; `due_at` still has not RRULE-advanced; live effort still shows 25/35. |
| **Proposed recovery (recommendation — not impl)** | See quantitative table below. Catch-up and next-normal then coexist — **proposed, not supported today.** |
| **What operator chooses today** | leave-held · skip · **release** same-task under new dates. Recovery authorize is **not** an available action until unlocked. |

### Quantitative after proposed recovery

| Identity | Attributable history | Live `worked_minutes` | Live `remaining_minutes` | Scheduler / P0 effect |
| --- | --- | --- | --- | --- |
| **Miss episode (historical)** | Disposition row + immutable `bounds_snapshot` + `episode_key`; recommended snapshot of miss-era worked total (= **25**) and progress-entry ids on the disposition **before** live reset. Append-only `task_progress_entries` stay on series `task_id` (corrections must remain same-task). | n/a (not a live schedulable identity) | n/a | No placement; miss tip already recorded |
| **Catch-up one-off** (new Task) | Own new ledger after create; link to miss episode. **Does not** receive the historical 25. | **0** at create (`initialize_task_effort_on_create`) — means **no minutes logged yet on this identity**, **not** “zero remaining work” | **Default = last confirmed remaining** (**35** in example), **editable at review** — not automatic full restart to **60** (Dex lean; still Trish confirm via Dex / §7 choice 2) | Placed as ordinary one-off under reviewed usable bounds (e.g. Wed 2026-08-13 14:00–16:00). Completing catch-up logs new minutes **only** on this Task; does **not** advance series |
| **Series next-normal** (same live Task, advanced) | Same series `task_id` keeps historical progress rows (25 attributable to miss era via timestamps + disposition snapshot). | **0** after recovery reset — miss-era 25 must **not** remain as live worked | **60** (original estimate) after recovery reset — miss-era 35 must **not** shrink next week’s remaining | After reset + bounds roll to Tue 2026-08-18: `worked_minutes > 0` inflight hold does **not** fire from miss-era work; `placement_effort_minutes` uses **60**, not 35. Fingerprint sees fresh worked/remaining. Completing next-normal later uses ordinary `complete_task` |

**Why miss-era 25 on the same live Task must not count for next-normal:**  
`worked_minutes` and `remaining_minutes` are **live occurrence columns** on the single series row. Placement uses `remaining_minutes` (`placement_effort_minutes`). P0 / inflight hold (`in_flight_hold_trigger`) is true when `worked_minutes > 0` (and start-window bounds are set) → `occurrence_bounds_hold_inflight`, skip new placement. If recovery (or today’s `complete_task`) advances `due_at` but leaves `worked=25` / `remaining=35`, next week’s occurrence is treated as **already begun with 35 left** — contaminating effort and falsely holding placement. The 25 is real miss-era work; it belongs in **history/ledger + disposition snapshot**, not in next-normal’s live columns.

**Avoid both lost history and contamination (recommended pair):**

1. **Keep history:** leave `task_progress_entries` on the series `task_id`; snapshot worked total + entry ids onto the miss disposition before mutating live columns; do not delete or move ledger rows to the catch-up.
2. **Prevent contamination:** on series advance for recovery, set live `worked_minutes = 0` and `remaining_minutes = estimated_duration_minutes` (next-normal full estimate); never copy the 25 onto the catch-up; catch-up inits fresh via `initialize_task_effort_on_create`.

### Short note — one-off (release sufficient)

Same clock, **non-recurring** “File Q2 receipts” missed 09:00–11:00. Intent is retry the same task under Wed afternoon dates → **date-first release**. Recovery adds nothing. Effort stays on the same task (correct for R-retry).

## 5. Engineering recommendation — persistence shape (not a Trish menu)

**Inspected callers (read-only; Tesla + local):**

| Area | Callers / hard edges |
| --- | --- |
| Effort columns | `Task.estimated_duration_minutes` / `worked_minutes` / `remaining_minutes`; API `original_estimate_minutes` / `time_worked_minutes` / `remaining_estimate_minutes`. Remaining is **stored independently** — not `original − worked`. |
| Create | `initialize_task_effort_on_create` → worked 0, remaining = estimate |
| Log | `append_progress_entry` (`POST /tasks/{id}/progress-entries`) → `worked += minutes`; **assigns** client-supplied remaining; ledger row on that `task_id`; corrections constrained same-task |
| PATCH | `apply_task_patch` may set remaining; original estimate immutable (`ORIGINAL_ESTIMATE_IMMUTABLE`) |
| Placement | `placement_effort_minutes` → remaining else original; fingerprint v4 hashes original/worked/remaining separately |
| P0 / inflight | `in_flight_hold_trigger` in `occurrence_bounds.py` when `worked_minutes > 0` (with start bounds) → hold_inflight, no new place |
| Series advance today | `complete_task` writes **only** `due_at`; no effort reset; **no bounds roll** |
| Disposition | `episode_key` from bounds+deadline only; progress not in key |

**Recommend:** materialize catch-up as a **new authored one-off `Task`**, linked to the miss disposition / `episode_key` (link table or disposition fields — impl detail later), plus a **dedicated series-advance helper** that (a) snapshots miss-era progress onto the disposition, (b) writes next RRULE `due_at` + **bounds/deadline roll** (§5.1), (c) resets live series effort columns (§6), **without** going through `complete_task`.

**Why (substantiated from current schema/callers):**

- There is **no occurrence table**; the series is one live `Task` row. A second live occurrence cannot be “another disposition resolution” without inventing work identity the schema does not have.
- Disposition rows are **hold/miss evidence**, not schedulable work. Release/skip already terminalize them without creating Tasks.
- Progress ledger and corrections are **per `task_id`** with no episode_key — attribution to a miss is “this task, these entry timestamps,” plus whatever snapshot recovery writes on the disposition.
- `complete_task` is the only RRULE writer and it **means** occurrence completed; it also **fails** to reset effort or roll bounds. Reusing it for “advance past miss” would encode false complete **and** leave contamination.
- Events alone (`resolution=recovered` without a Task) cannot place catch-up on the board or accept progress without still inventing a work row.
- A new one-off gets its own id and clean effort init; it does not see the series ledger — which is what we want for non-duplication.

**Not a product menu:** Task vs link vs event vs resolution is eng follow-through after scope is accepted. Do not ask Trish to pick a persistence shape.

If that instant is still in the past relative to operator “now,” **do not** auto-loop to “next future” inside recovery — past landing must be **explicitly reviewed** (accept past next-normal dates, or step further / PATCH). Document honesty: today’s fixed `complete_task` also steps once into the past. **Completion-anchored (`is_fixed=false`):** without a real complete, recovery must pick an explicit anchor — **propose** (user-visible cadence rule, **not** silently settled eng policy) treat recovery authorization time as the completion-equivalent anchor (first instant strictly after authorize/`now` in the rule zone), matching today’s completion-anchored skip-of-intermediate-slots. Do **not** invent multi-miss catch-up Tasks automatically. |
| **Fixed vs completion-anchored** | Preserve the rule’s `is_fixed` semantics for *which* next instant is chosen (table above). Authorize-as-anchor for completion-anchored remains a **proposed user-visible cadence rule** pending Trish via Dex — not eng fiat. |

## 6. P0 / never duplicate logged work (concrete)

**Settled P0 (do not reopen):** logged `worked_minutes > 0` is the system-recorded evidence of work begun; zero does not prove no off-record work; pin/reserve/started are preservation only.

**Column vs ledger (code truth):**

- **Live columns** on `tasks`: `worked_minutes`, `remaining_minutes` (nullable; reads fall back to estimate), `estimated_duration_minutes`.
- **Ledger:** `task_progress_entries` append-only; each row has `minutes_worked` + confirmed `remaining_minutes` at log time; keyed by `task_id` only.
- Remaining is **not** computed as original − worked; client supplies remaining on progress POST.

**Recommended progress rule for recovery:**

| Identity | Live worked | Live remaining | Ledger / history |
| --- | --- | --- | --- |
| Series **before** recovery | 25 (miss-era) | 35 | Entries totaling 25 on series `task_id` |
| Series **after** recovery (next-normal) | **0** | **60** (original) | **Same** historical entries retained; disposition holds snapshot of miss-era 25 |
| Catch-up one-off **at create** | **0** | **Default last confirmed remaining (35)**; **editable at review** — not automatic full restart to **60** (Dex lean; Trish confirm via Dex) | Empty until new logs |

**Clarify (pass-2 error fixed):** Catch-up `worked_minutes = 0` means **no minutes have been logged on the catch-up identity yet**. It does **not** mean remaining work is zero. Remaining on the catch-up is its own `remaining_minutes` (initialized to its estimate). Saying “shows 0 remaining work to log afresh” was wrong.

**Never:** copy, split, or double-count the same 25 onto both live identities; leave live series at 25/35 after advance; delete series ledger rows to “move” history onto catch-up.

Any other user-visible progress rule is a genuine product override (§7 choice 2) — not an eng freebie.
