## 1. Today’s series transition (code-backed) vs proposed

### Today — how next normal is reached

**One-liner:** Next normal is **not** reached on leave / release / skip / scheduler; only `complete_task` overwrites the single `Task.due_at` via `next_due_at` (or a human PATCHes `due_at`).

| Fact | Code path |
| --- | --- |
| Sole RRULE advance | `POST /tasks/{id}/complete` → `complete_task` (`task_helpers.py`) → `recurrence.next_due_at` → `task.due_at = nxt`; task stays open. Board `done` → `transition_task_workflow` → same `complete_task`. |
| What `next_due_at` is | Function in `recurrence.py`, not a stored “next normal” row. One step past anchor (`is_fixed` → previous due; else → `completed_at`). Multi-week miss does **not** jump to the next still-future slot. |
| Schema | One `Task` + optional one `recurrence_rules` row. **No occurrence table.** Held miss = `task_occurrence_dispositions` only. |
| Held insert | `stage_auto_misses` writes `unresolved_held`; does **not** move `due_at` / bounds / completion. |
| While held | `calculate` skips placement for that `task_id`. Leave-held = event only. |
| `release_held` | Clears hold; optional live **bounds** patch; **no** `due_at`, **no** `next_due_at`, **no** `complete_task`. |
| `skip_held` | `resolution=skipped`; **no** date writes; task stays skipped for placement. |
| Scheduler | `apps/api/app/scheduler/` does not import recurrence; **no** advance-without-complete tick. |
| Manual escape | `PATCH` task may set `due_at` by hand — not an RRULE step. |

**Honesty:** Completing a held miss to “get to next week” **is** false-completing that missed work from a product view: the system advances the series by treating the occurrence as completed. Leave/release/skip leave the live task stuck on the missed occurrence.

**Do not claim:** next-normal coexistence with an unrecovered miss is already supported. It is not.

### Proposed — only if recovery ships (not implemented)

Recovery would add a **new** path that:

1. Authors a **distinct one-off** for the missed episode (catch-up identity).
2. Advances the **series** pointer (`due_at` + the occurrence bounds the miss detector uses — today `complete_task` rolls only `due_at`) to the next RRULE instant **without** calling `complete_task` on the miss.
3. Clears or terminals the task-wide hold so the series task is schedulable for next-normal (release clears hold but does not advance; recovery must do both, or equivalent).
4. Ensures completing the catch-up one-off does **not** invoke the series task’s `complete_task`.

Until that path exists, “catch-up beside next-normal” is **proposed product**, not current behavior.

## 3. Release vs recovery (unchanged honesty)

### Release already accomplishes (R-retry)

- Operator reviews / sets **usable dates** (PATCH then POST release, or atomic bounds on release).
- Preserves disposition id / episode_key / snapshot history of the miss.
- Clears held → task is again schedulable under reviewed bounds.
- Temporal gate only (`BOUNDS_STILL_MISSED` + nested savepoint rollback). Free-slot / horizon is ordinary calculate after release — not a release concern.
- **Does not** create a second identity; **does not** advance `due_at` / RRULE.

### When recovery adds nothing

| Case | Why release (or leave/skip) is enough |
| --- | --- |
| One-off / stand-in with no series | Catch-up *is* retrying the same live task |
| Intent is retry-same-task under new dates | That is exactly R-retry |
| Skip forever | `skip_held` — no catch-up wanted |
| Leave-held only | Operator not ready; no new identity needed |
| Post-release no-slot / horizon miss | Ordinary calculate/place — not a new disposition kind |

### When recovery would genuinely differ

| Case | Why release alone is insufficient |
| --- | --- |
| **Recurring — catch-up beside next normal** | Release retargets the **single** live task. Catch-up that must **coexist** with next-normal needs a distinct authored one-off **plus** a series advance that is not `complete_task` on the miss. **Neither exists today.** |
| **After S-suppress** | Skip is task-wide; dates do not un-skip. Reactivation path is not release. **Separate later question — not in min useful scope.** |
| **Preserve miss as history while catch-up is separate** | Want miss row historical while a new one-off carries catch-up — without rewriting series dates via release alone. Covered by the recurring min scope when that ships. |

**Code today:** no recovery resolution, event, route, or service.

## 5. Engineering recommendation — persistence shape (not a Trish menu)

**Recommend:** materialize catch-up as a **new authored one-off `Task`**, linked to the miss disposition / `episode_key` (link table or disposition fields — impl detail later), plus a **dedicated series-advance helper** that writes next RRULE `due_at` (+ occurrence bounds roll) **without** going through `complete_task`.

**Why (substantiated from current schema/callers):**

- There is **no occurrence table**; the series is one live `Task` row. A second live occurrence cannot be “another disposition resolution” without inventing work identity the schema does not have.
- Disposition rows are **hold/miss evidence**, not schedulable work. Release/skip already terminalize them without creating Tasks.
- `complete_task` is the only RRULE writer and it **means** occurrence completed. Reusing it for “advance past miss” would encode false complete.
- Events alone (`resolution=recovered` without a Task) cannot place catch-up on the board or accept progress without still inventing a work row.

**Not a product menu:** Task vs link vs event vs resolution is eng follow-through after scope is accepted. Do not ask Trish to pick a persistence shape.

### Contract-level requirements (if product keeps recovery)

| Concern | Requirement |
| --- | --- |
| Duplicate / retry protection | Named target identity; idempotent terminal behavior; no double catch-up for same episode without explicit re-auth |
| Bounds validation | Same usable-dates discipline as release (temporal gate); fail closed on still-missed bounds |
| Stale revision | Stale `scheduling_revision` → conflict (parity with release/skip 409 pattern) |
| Cancellation / rollback | Nested savepoint / txn rollback on gate fail; no half-written catch-up |
| No automatic backlog | Operator-reviewed only; no silent stacking; no auto multi-miss fan-out |
| No silent stacking | Catch-up must not merge into next-normal or invent parallel holds without disposition |
| Series advance | Explicit non-`complete_task` path; catch-up complete must not advance series |

## 6. P0 / never duplicate logged work (concrete)

**Settled P0 (do not reopen):** logged `worked_minutes > 0` is the system-recorded evidence of work begun; zero does not prove no off-record work; pin/reserve/started are preservation only.

**Recommended progress rule for recovery:**

- Series task keeps its existing `worked_minutes` (P0 signal of miss-era logged work).
- Catch-up one-off starts at **`worked_minutes = 0`**.
- **Never** copy, split, or double-count logged minutes onto both identities.
- No silent transfer UI in the min scope.

**Concrete example:** Weekly books had `worked_minutes = 25` before the Tue 2026-08-11 window was held. Operator authorizes recovery for Wed 2026-08-13 catch-up. After recovery: series task still shows **25** (begun-work signal for the missed episode era); catch-up one-off shows **0** remaining work to log afresh; board/calculate must not present **50** or two copies of the same 25. Completing the catch-up logs new minutes only on the one-off.

Any other user-visible progress rule is a genuine product override (§7 choice 2) — not an eng freebie.
