### S1-D1 — Preserve Working weekdays across the compatibility bridge

**Source:** [`availability_policies.py`](../../apps/api/app/services/availability_policies.py), `_sync_workweek_from_working_windows`; [`placement.py`](../../apps/api/app/scheduler/placement.py), `is_workday`.

A Tuesday–Saturday pattern passes the contiguous-days check and becomes `workweek_days = 5`. The legacy scheduler interprets that as Monday–Friday. Dex's isolated execution confirmed Monday eligible and Saturday excluded. Only representable Monday-first patterns should update the legacy mirrors; other patterns need explicit rejection or config-only handling without changing legacy eligibility.

**Retest:** Tue–Sat and weekend-only patterns must not silently become different weekdays. Verify Monday-first patterns still round-trip and confirm the chosen rejection/config-only behavior in the API response and stored mirrors.

### S1-D2 — Enforce stale protection for both remaining-work write paths

**Source:** [`progress.py`](../../apps/api/app/schemas/progress.py), `TaskProgressEntryCreate`; [`task_progress.py`](../../apps/api/app/services/task_progress.py), `_assert_scheduling_revision`; [`task_patch.py`](../../apps/api/app/services/task_patch.py), `apply_task_patch`.

Progress requests may omit `expected_revision`, bypassing the guard; remaining-only PATCH has no revision check. A prepared estimate can overwrite a newer confirmed remaining value. Contract §1.2 requires stale protection for both operations. Dex confirmed the progress schema accepts omission and the guard accepts it at an arbitrary current revision; PATCH exposure was established by source review.

**Retest:** Prepare two actions from the same state, commit one, and ensure the second is rejected without a log or remaining-value mutation. Cover progress and remaining-only edits, missing tokens, valid fresh writes, and same-key retries of an already committed action.

### S1-D3 — Refresh progress state after acquiring the lock

**Source:** [`tasks.py`](../../apps/api/app/api/routes/tasks.py), progress endpoint; [`task_progress.py`](../../apps/api/app/services/task_progress.py), locked task read and worked-total increment.

The route loads the task before the scheduling lock. The later `FOR UPDATE` query does not refresh an existing SQLAlchemy identity-map object. With distinct keys and omitted revisions, two progress entries can persist while the second total increment uses stale worked minutes. Refresh under the lock or use an atomic database increment, alongside S1-D2's stale-state protection.

**Evidence boundary:** Dex reproduced the identity-map behavior using the actual Task mapper against a minimal in-memory SQLite table: a database total of 20 remained 0 in the loaded object; adding 30 stored 30 instead of 50. This demonstrates the stale-object mechanism, **not** PostgreSQL locking/concurrency behavior.

**Retest:** Use independent PostgreSQL sessions and controlled interleaving. Ensure successful entries reconcile with the task's worked total; stale rejected actions leave no entry or partial update. Include idempotent concurrent retries. Do not mark PostgreSQL concurrency verified from the SQLite reproduction alone.

**Quality result (Renee, 2026-10-12) — not a Dex retest:** An earlier independent-session run failed `test_overlapping_same_key_retry_replays_once` with 409 `SCHEDULING_REVISION_CONFLICT`: the waiter looked up the idempotency key before `lock_owner_scheduling`, missed the uncommitted row, then failed the revision check after the holder committed. Jules re-queries the key after the lock and replays without a second insert. Rerun on `theplan_s1_test` ([`test_s1_d3_pg_concurrency.py`](../../apps/api/tests/test_s1_d3_pg_concurrency.py), **4 passed**): two open connections sum 20+30 to worked 50; a session that still holds `worked_minutes == 0` after another connection commits +20 then applies +30 and stores 50; an overlapping stale revision is rejected with no extra entry and no partial remaining/worked update; the overlapping same-key retry replays once.

### S1-D5 — Empty Working must have a supported, coherent outcome

**Sources:** [`availability_policies.py`](../../apps/api/app/services/availability_policies.py), `_sync_workweek_from_working_windows` and `update_policy`; [`settings.py`](../../apps/api/app/schemas/settings.py), `UserSettingsUpdate` (currently rejects zero); legacy database `user_settings_workweek_days_check`.

The exposed availability PATCH accepts `{"windows":[]}`. The mirror helper assigns zero workdays, and the revision increment flush raises an unhandled `IntegrityError`. The service-level PostgreSQL reproduction returned: `new row for relation "user_settings" violates check constraint "user_settings_workweek_days_check"`. The route does not translate that database exception into an actionable domain error. This is an exposed failure path, not merely a future scheduling edge.

**Expected / fix direction:** The contract permits empty Working as no Working days. Align the deployed constraint and supported read/write validation with that behavior, or explicitly stage empty Working as config-only with unchanged mirrors and clear disclosure until activation. Do not silently substitute a nonempty week. If the team must temporarily reject the operation, return a clear validation error and keep this capability limitation documented rather than claiming empty-policy support.

**Retest required:** Against a database migrated from the prior schema, PATCH Working to empty through the API/CLI. Verify the agreed response, persisted policy and mirrors, revision behavior, and absence of partial writes or a 500. Restore a nonempty Monday-first pattern and verify round-trip. Unit tests of the mirror helper alone cannot catch this database constraint mismatch.
