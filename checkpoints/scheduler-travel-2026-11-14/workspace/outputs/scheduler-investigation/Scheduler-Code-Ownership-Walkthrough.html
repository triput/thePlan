Your Scheduler: where to look, and what to protect

A reading route for Trish and Dex. You do not need to read every line to understand the consequential decisions. For each file, start with the responsibility, the possible consequence, and the rule we want the code to preserve. Then we can follow one concrete example through the named function.

Start with three stops: the transaction outcome (1), the database acknowledgment (2), and ownership and lock order (5). Those answer: Did the change happen? How do we know? And were we allowed to change that calendar?

This guide describes a frozen, unactivated workspace candidate. All 12 source hashes and named line anchors were checked against the reading map when this guide was made. It is an index for understanding the code, not proof that every described behavior has passed in the complete Scheduler.

Keep source, checks, and runtime evidence separate

A function can express the right rule while its integration still needs proof. Native v9 established its bounded transaction and SQL cases. I01/I02 established their HTTP/native assessment and owner-lock cases using a fixture transport. The current default-HTTPS provider composition has stopped during verification; those failures and their cleanup receipts are preserved. The new peer-close correction is prepared, with its fake verification awaiting approval when this guide was written. It has no native PASS yet.

For a spot check, ask three questions: What rule does this function enforce? Which exact check or receipt exercises it? What remains outside that evidence? We will use the current consolidated plan and actual result files to answer the last two. No family label or green check replaces that comparison.

The test and launch files get a separate walkthrough

After the production path, we should inspect the runner's assertions and sanitized failure report, the host supervisor's admission and disposal rules, the immutable Docker transport's identity and retirement checks, and the fake checker's oracles. A defect in the test harness can mislead us too; the recent peer listener and checker issues are useful examples.

This guide adds no execution, deployment, provider access, or endpoint authority. It is not a new review gate or a reading assignment. We can choose the next stop together.
